# 业务优先级信号提案（priority_proposal）

本轮有客观业务影响、处理期限或下述升级信号时按 Schema 输出提案；更新旧事项且本轮无新线索时填 `null`（`duplicate` 与 `review` 固定填 `null`）。程序会结合客户等级库计算最终优先级，模型不得读取或猜测客户等级：

- **客观影响面（`impact`）**
  - `critical`：已证实大范围关键生产中断且无绕行，或正在发生重大安全、资损事故。`evidence_ids` 和 `quote` 必须直接引用证实事故的原文。证据不足时按已知影响填写，影响不明填 `unknown`。
  - `high`：核心功能严重受阻且无绕行方案、持续高频生产报错、明确执行迁离或核心合作终止。
  - `medium`：局部接口或节点异常、批量请求报错或耗时显著退化、条件性流失警告、阻塞既定上线或交付节点。
  - `low`：个别或少量请求报错与慢请求核查、常规链路与配置排查、常规资源调整、功能改善、日常报价账单开票续费、技术核验与培训。
  - `unknown`：仅用于完全无法判断具体问题的残缺片段；只要已指出具体报错、慢请求或明确诉求，必须按实际范围选 `low`～`critical`。
- **时效紧迫度（`urgency`）**
  - `immediate`：线上业务持续受损，或原文明确当日截止死线。
  - `soon`：原文明确近期交付/上线/办理节点，或线上报错需当班尽快定位。
  - `normal`：常规排查、排期评估或一般日常跟进。
  - `unknown`：原文未提任何时效线索（不影响按客观 `impact` 定级）。单句“尽快”而无客观中断依据时，不得虚标为 `critical`。


明显情绪升级填 `escalated_emotion`，强催办填 `strong_followup`。证据只引用最新一条已确认客户就本事项发出的 `question` 原话，`evidence_ids` 填这一条消息的 ID。仅因催办新增提案时，客观维度缺少新证据填 `unknown`。
明确要求升级或负责人介入可直接成立。以重复催办为依据时，`strong_followup.previous_message_id` 引用同一待回复轮次的更早催办，可以引用已保存 `reply_round` 的原消息，格式 `来源:消息ID`。普通的单句“尽快”、表情、转述或无关消息均不足以提档。
