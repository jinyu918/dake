# 事项分类与属性规范

## 一、适用口径

本规范用于从沟通中识别可跟进事项，确定类型、属性、证据、事项身份及后续变化。六类为商机、流失、排障、资源需求、功能需求、商务需求；同一事项允许多个有证据的标签，不用其他分类体系替代六类。

六类及公共属性要求以[项目简报](项目简报.md)为依据；多标签、逐项证据、跨天延续、复发、纠正和拆分按已认可的业务方向细化。本文的跟进状态、商机阶段、事实性质用语是建议口径；官方尚未正式公布状态和等级枚举，不能把这些建议用语称为官方枚举。具体等级规则未明确前，保留原话和已确认依据，不能自行定出等级。

本文采用以下业务前提：

- 识别单元是具体事项；消息、群、标签、处理阶段本身都不是事项身份。
- 事项需要真实依据，但不要求资料齐全。没有数量、日期、负责人、根因或等级，仍可能构成事项。
- 咨询可形成服务责任。判断是否存在具体对象、待答复问题、核验或交付结果，不能仅凭“咨询”一词排除。
- 已发生事实也可形成需记录和跟进的事项；普通背景事实不会仅因包含数字、产品名或时间就成为事项。

## 二、核心概念与最低识别依据

| 业务概念 | 精确定义 | 判断要求 |
| --- | --- | --- |
| 事项 | 围绕可辨认的业务对象和具体目标、问题或结果，可以持续追踪请求、处理、结果或后续责任的业务单元 | 可以是提出的诉求、发生的异常、明确的机会或流失变化，也可以是已发生且有独立业务意义的结果；不等同于每一句话 |
| 类型标签 | 对事项中已经有证据的业务性质作出的判断 | 每个标签分别证明；标签可增加、撤销或更正，事项身份不随之自动变化 |
| 业务事实 | 沟通中关于对象、行为、数量、条件、时间、结果等可核对的陈述 | 区分请求、意向、计划、假设、他人转述、观察、核实结果及否定；“有人这样说”不等于内容已被验证 |
| 事项进展 | 对同一事项增加或改变了当前业务认知、待办、处理动作、验证结果、承诺或判断的事实 | 新日志、再次确认仍失败、明确催办及期限变化均可能是进展；纯转发旧结论不是新进展 |
| 非事件 | 已理解的内容中，没有独立可跟进对象和目标，也没有给已有事项增加有效事实或进展 | 问候、表情、纯收悉、纯致谢、泛泛闲聊、无现实指向的知识问答；要与未读、没看懂、漏判区分 |
| 待确认 | 对事项是否成立、对象或归属、类型、字段或前后轮次仍存在需要补充证据才能解决的具体疑点 | 必须指出疑点及所缺依据；它是确认情况，不是第七种主类型，也不等于事项整体未处理 |
| 待分类 | 已有真实事项依据，但尚不能证明任何适用类型，也不能证明六类均不适用 | 保留事项及依据，标签暂不定；不能强塞“其他”或挑一个最像的六类 |

### 2.1 最低依据

确认一项事项至少具备三项内容，允许由上下文中的多条证据共同提供：

1. **现实指向**：是当前或明确回顾的真实业务表达，不是例句、假设演练、引用中的无关请求。
2. **可辨认对象**：可以确定到本次业务所需的产品、环境、资源、工单、交易、合同或服务对象；唯一明确的回复指向可补足省略的对象，不要求对象一定有编号。
3. **具体业务依据**：有明确请求、待解决问题、异常、行动或结果，能说清要跟什么或记录什么。例如“请核实A环境能否满足所列上线条件并答复”已经成立，无须先有负责人和承诺时间。

对象或目标无法确定时，先保留待确认线索，不凭猜测新建一个具体事项。事项本身已可定位、仅类型未定时，可以保留稳定的待分类事项。部分字段缺失时，事项照常成立，仅相应字段未知或待核实。

“请跟进”“那个还是不行”等语句有唯一清楚的上下文时更新对应事项；存在多个可能对象时待确认；完全没有可辨认上下文时不能补造对象。缺失上下文不等于无事件。

### 2.2 判断顺序

先读懂新增发言与必要引用，确认现实对象和具体目标；再与已有事项比较身份；随后逐标签、逐属性核对证据；最后判断跟进状态及各类业务事实。对一条消息中的每个独立语义片段分别判断，允许同条消息同时包含新事项、既有事项进展、非事件和待确认内容。

## 三、六类定义、最低标签证据与排除条件

### 3.1 商机

**定义**：客户对新增采购、增购、付费扩量、购买评估或以采购为目的的试用表达了具体意向、计划、行动或结果，值得跟进交易转化。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 明确要采购或增购；有业务用途的新增规模迁入；明确进入采购评估的试用；为具体采购决策索取方案或报价；具体交易已确认购买，需记录交易结果或后续履约 |
| 最低标签证据 | 有具体产品或服务对象，以及采购、增购、购买评估、商业扩量等表达；对象可由明确上下文补足。无需预先给出预算、成交概率、数量或采购日期 |
| 排除 | 泛泛问价格、问是否支持、只想了解；未表明采购目的的技术试用；内部为修故障扩容；客户申请已有权益内配额；仅历史用量增加，无商业意图证据 |
| 不可升级的结论 | 试用不等于购买，报价不等于接受，接受报价不等于签约，签约不自动等于付款、开通或收入确认；各结果分别记录 |

“先试试”可以是具体资源或服务请求，但不能凭这句话认定商机；“本次为购买A产品做试用评估”可标商机，购买事实仍未知。因已有需求而推测将来会增购，只能列待核实线索，不能增加商机标签。

### 3.2 流失

**定义**：客户减少、停止或转移既有合作、用量、产品使用或续约的风险、计划或实际变化。流失范围可以只涉及某产品、部分用量或某一期合同，不能扩大为整家客户流失。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 明确“再不恢复就迁走”等条件性离开；明确减量、迁移、停用或不续约计划；已经执行的减少或退出；明确取消尚未实施的退出计划也作为原事项更新 |
| 最低标签证据 | 能确定涉及的合作或使用对象，且有减少、停止、迁离、不续约等方向；允许条件性风险，不要求实际迁移已发生 |
| 排除 | 一般不满、价格高或催办；单次用量下降；临时维护、测试切流；供应方内部关渠道或停故障节点；只说合同快到期、正常办理续费 |
| 事实区分 | 风险表示可能或有条件发生；计划表示明确准备或决定但尚未执行；实际变化必须有执行证据。三者不能互相替代 |

客户“先停一下”需理解是临时排障动作还是停止合作；无法确定时流失标签待确认，不凭“停”字下结论。明确不续约可同时有商务办理内容，不能只归正常续费。

### 3.3 排障

**定义**：针对现有产品、服务、环境或约定能力出现的异常、失败、退化及其定位、处置、恢复和验证。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 客户反馈现有业务失败、明显异常或性能退化；核验疑似故障；补日志、诊断、修复、回滚及恢复确认；对已处置问题的复测和纠正 |
| 最低标签证据 | 有具体对象及异常现象或待核验的异常描述。客户报障可先成立，不要求已经证实供应方责任、找到根因或证明违反承诺 |
| 排除 | 尚未提供的新能力；无异常的常规用法咨询；在正常表现上提出新的性能目标；单纯增加资源额度；客户不适应现有设计但未说明异常 |
| 事实区分 | 症状、客户影响、诊断假设、已核实发现、处置、指标恢复、客户验证、根因是不同事实；修复动作不能代替恢复验证 |

“慢”若指原来正常现突然显著退化，可建排障，基线和影响不详则未知；“当前符合约定，但希望再快一倍”不是故障证据。投诉、测试失败可以支持排障，但不能直接证明根因或服务方过错。

### 3.4 资源需求

**定义**：在现有产品能力范围内，对客户可使用的容量、配额、规格、带宽、机器、实例、地域等技术资源提出开通、增加、减少、预留、切换或交付请求。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 明确配额申请、资源开通或规格调整；资源缺口要求补足；为上线申请预留；明确要求技术资源交付或变更，即使尚未给出数量 |
| 最低标签证据 | 有资源对象和客户交付/调整目标或明确申请动作。数量、缺口或期望时间有任一项并不能单独代替请求；明确“请提高A配额，具体数值待测算”已足够 |
| 排除 | 内部为恢复服务进行扩容、调度、降权或参数调整；泛泛讨论资源；单纯性能抱怨；新增产品能力；已知使用量上升但没人提出资源诉求 |
| 事实区分 | 请求量、现有量、目标总量、增减量、获批量、实际交付量和可用验证分别判断；申请不等于批准，批准不等于交付 |

内部人员转述“客户申请提高A配额”可支持请求已被转述，不能因为发言者是内部人员一概排除；必须保留转述性质。内部“我扩了几个节点，故障先观察”仅为故障处置。

### 3.5 功能需求

**定义**：要求新增、开放、改变或改善产品对外可感知的能力、行为、操作方式、适用范围或性能表现，目标超出现有故障恢复或既有资源交付。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 新能力、新接入、新权限行为；对已有功能的修改或改善；改善交互、准确性、响应时间、吞吐等产品表现；明确要求形成产品变化的具体结果 |
| 最低标签证据 | 有可辨认能力/场景及希望达到的新行为或改善方向。无需先提供完整需求文档、验收数值或实现方案；“希望A导出支持取消任务”可成立 |
| 排除 | 仅问当前是否支持；要求恢复本应具备的行为；只调整已有额度、规格或配置即可交付且没有产品能力变化；无具体方向的“优化一下” |
| 事实区分 | 客户提出、可行性答复、接受评估、承诺范围、已上线、已验证分别记录。接收建议不等于承诺开发，上线不等于满足客户需求 |

**优化已有功能可以是功能需求。** 判断的是改善目标而非“已有”二字。为恢复原有正常表现而优化属于排障处置；交付现有大规格资源以满足目标属于资源需求；要求产品产生新的可感知表现，属于功能需求。不能因为可能需要改代码就自动判功能，也不能因为叫“优化”就排除功能。

### 3.6 商务需求

**定义**：关于具体交易或合作的价格、报价、折扣、合同、续费办理、账单、发票、付款、退款、赔付或结算等商务答复与办理事项。

| 项目 | 业务规则 |
| --- | --- |
| 纳入 | 对当前具体交易或服务明确索价；处理报价、合同条款、续费手续、账单争议、开票、付款、退款等；业务咨询需形成具体商务答复时也纳入 |
| 最低标签证据 | 有商务对象及待答复、核对或办理内容。“A服务怎么计费”有明确答复对象，可建商务事项；不要求采购意向或金额已经确定 |
| 排除 | 无现实对象的价格话题；纯技术使用说明；内部资源动作；没有任何商务办理内容的普通抱怨；只有系统异常且未涉及商务处理 |
| 事实区分 | 询价、出价、接受、合同确认、付款、开票、到账、退款各为独立事实；不以一句“好了”推断所有环节完成 |

普通询价可以是商务事项，但不能顺带标商机；单纯转发价目表、没有具体请求且没有新增业务事实时，不单独建事项。

### 3.7 容易混淆的成对边界

| 边界 | 决定依据 | 可共存的条件 |
| --- | --- | --- |
| 商机 / 商务需求 | 商机需要采购或购买评估等意向；商务需要具体价格或办理责任 | 为明确增购索取报价，可同一事项双标签；付款与独立新采购不同则拆分 |
| 商机 / 资源需求 | 扩商业购买与交付技术资源不同；已有权益内提额不证明销售机会 | 明确付费增购本次配额，可同一事项双标签 |
| 商机 / 功能需求 | 采购评估与产品变化请求各须证据 | “若支持A能力就采购，并请提供该能力”可双标签；仅想象未来销量不成立 |
| 流失 / 排障 | 故障或抱怨不等于离开；流失须出现合作减少或退出方向 | 为同一恢复目标明确“再不恢复就迁走”可双标签；已另起迁移执行且独立验收则拆分 |
| 流失 / 商务需求 | 正常续费仅为商务；不续约属于计划或实际流失 | 同一期合同不续约并要求办理终止手续，可双标签；别的合同续费不并入 |
| 流失 / 资源需求 | 调低配额、调整规格本身不证明合作或业务使用减少 | 明确为缩减既有业务而减少资源，才分别核对两个标签；临时调整或收回闲置额度不直接标流失 |
| 排障 / 功能需求 | 恢复已有预期还是改变预期；不以内部采用何种修复方法区分 | 同一目标确有“修复异常”和“增加新行为”两项证据才可双标签；能各自验收时拆分 |
| 排障 / 资源需求 | 内部处置与面向客户的资源请求分开 | 客户明确要求本次提额作为恢复目标且同一次验收，可双标签；内部扩容不能补标签 |
| 资源需求 / 功能需求 | 请求现有资源交付还是产品能力变化 | 同一不可独立验收的交付确实同时包含资源与新能力时可双标签；一般的两个目标分别跟进 |
| 咨询 / 服务事项 | 是否有现实对象和明确答复、核验、讲解或服务结果 | 咨询不是主类型；按已成立内容归六类，确实超出六类时按“其他”规则 |
| 功能性能改善 / 容量诉求 / 性能故障 | 新性能目标归功能；明确现有资源交付归资源；现有表现异常归排障 | 分别有证据才能多标签；“性能”一词本身不决定类型 |

同一性能目标尚不能判断是异常、现有规格不足还是新增能力时，记录现象和目标并待分类；不要从“延迟高”反推资源不足或根因。已有排障依据但资源方案未确定时，保留排障，资源标签不定，不把整个事项降为无事件。

## 四、多标签、事项身份与拆分

### 4.1 同一事项身份

比较同一客户下的具体对象、目标、发生轮次及处理连续性，并检查结果是否可独立验收。编号、引用、产品环境、现象和明确衔接语可相互补充。工单相同是强线索，但一个工单内仍可能有多个独立目标；不同工单也可能只是同一事项的流转。

类型、日期、群、参与人员、标题、阶段名称和当前状态都不单独定义身份。标签增加、撤销或纠正时保持事项身份；同一对象由咨询到报价、确认、交付、验证，若仍服务同一目标，继续同一事项。新阶段只有产生独立对象、独立目标或可独立验收结果时才拆出事项，不能见到“上线”“验证”“重新排查”就新建。

一个事项中可同时有多个有证据标签；不能为了覆盖六类重复建同一事项，也不能为了减少条目而把不同事项合成一个。每个标签描述同一目标中的一种业务性质，不能借同条消息中的另一话题为它补证据。

### 4.2 应拆分的情形

| 情形 | 判断与处理 |
| --- | --- |
| 对象不同 | A空间下载故障与B空间上传故障分别跟进，除非证据明确为同一共同故障及统一恢复结果；仅同错误码不够 |
| 目标可独立验收 | 恢复下载与新增审计导出分别有独立结果，应拆分，即使同一消息、同一人、同一工单提出 |
| 新发生轮次 | 有新的发生窗口、请求批次或明确重新发生证据，足以区分上一轮时新建；不以固定间隔判断 |
| 前次恢复后复发 | 已有可信的恢复事实，之后同一对象同类问题再次发生，新建本轮并记录有证据的复发关系；前次不因此自动改成仍未恢复 |
| 无前次完成但有新独立轮次 | 明确是另一场活动、另一批资源申请或另一影响窗口，可独立跟进，无需等前次正式关闭；证据不足时待确认 |
| 原混合事项纠正 | 原身份保留给能认回的核心事项，其他独立事项分别归入已有事项或拆出；记录原分配的纠正，不保留一个重复覆盖全部内容的总事项 |

同阶段补日志、催办、澄清、改方案、复测或重申仍失败通常更新原事项。仅有时间空档、“又”“还是”、同产品、同人员或同错误码，都不足以证明延续或复发。

一条消息可同时回顾前次恢复和报告本次复发，分别支撑两轮；同一消息也可提供多个独立事项的不同片段。不得为满足“一条消息只归一处”而丢弃业务内容。共享原文必须分别说明支撑的是哪个片段；无关历史仅帮助理解，不延长新轮次的发生范围。

### 4.3 跨群的同一事项与关联事项

- 同一客户、同一对象和目标、同一轮次，有明确工单、引用或连续处理证据，即使跨群也应认回同一事项。
- 同一客户但对象或验收结果独立，只存在原因、前后承接、复发或共同背景时，保留多个事项，并仅在有证据时记录关系。
- 群相同不能证明同一事项；群不同不能证明不同事项。相同人员、关键词或一天内出现，不足以自动合并或关联。
- 客户身份不清、多个对象都可能被指代时待确认。跨客户的共同故障可记业务关联，但不得把不同客户的责任、结果和证据合成一个客户事项。

### 4.4 “其他”、待分类与非事件

| 情况 | 业务处理 |
| --- | --- |
| 六类均不适用，真实服务目标清楚 | 可单独使用“其他”，写明真实事项依据、具体服务结果及排除六类的理由。例如面向既有产品的专项使用培训，没有采购、异常、资源、新能力或商务办理 |
| 六类之一已经有证据，另有不可分割的六类外服务内容 | 可与“其他”共存，但必须指出“其他”具体代表哪项额外内容、它为何不在六类内、为何与当前目标不能独立验收；排除理由仅针对这项额外内容，不能声称整个事项不属于六类 |
| 六类内容与额外服务各有独立目标或验收 | 拆为六类事项与其他事项，可有业务关系；不能靠多标签掩盖两个事项 |
| 事项真实，但无法排除六类或无法确定类型 | 待分类；有证据的标签保留，仅未定部分待确认；不能把“不知道是哪类”解释成“不属于六类” |
| 未能读懂或附件未读 | 记录未读或具体歧义；正文已有事项可先成立，附件部分仍待确认，不凭附件名补事实 |
| 已理解且没有事项依据 | 非事件；不能因“其他”存在就把闲聊、普通知识讨论或纯收悉收入其中 |

“其他”的排除理由要回应实际可能的六类边界，不能只写“其他服务”“不属于上述”。日常沟通、正常实施说明、普通验收配合属于原事项的处理方式，不足以另加“其他”；只有额外服务义务本身有明确依据时才考虑共存。后续证明可归六类时，移除原“其他”或收窄其含义并记录更正，事项身份不变。

## 五、属性通用规则

以下字典定义业务记录内容，不要求把每一项变成建项必填条件，也不要求每项单独设置一个展示字段。仅识别事项所需的最低依据和实际已采用的标签必须有证据；其他字段按已有信息填写。

### 5.1 原话、解释和缺失

每个有值的标签或属性都应能回到具体原文片段、消息来源、发送时间及当时版本。原话与标准化解释分开：原话保持原意、条件和否定；解释可以统一单位写法、产品别名或事实性质，但必须说明对应关系，不能添入原话没有的事实。解释不是新的直接证据。对“我来跟进”等省略句可结合已确认发言者身份表达负责人；不能根据最后发言或被提及猜负责人。

缺失只使用以下三种业务含义，不用空串、零值、“无”或任意默认值混代：

| 表达 | 何时使用 | 操作规则 |
| --- | --- | --- |
| 未知 | 该信息可能适用，但当前资料没有说或尚未提供 | 不填猜测值；后续有直接依据时补充。没有根因、没提负责人即为未知 |
| 不适用 | 按已确认的事项事实，该属性不发生或没有业务意义 | 必须有判断理由。例如未成交的试用尚无实际成交金额；不能因尚未询问就写不适用 |
| 待核实 | 已有候选说法，但存在冲突、指代不明、条件未核实或来源需要确认 | 保留候选及疑点，不把任一候选作为确认值；有澄清后再更正 |

明确“没有负责人”“零新增”“不需开票”是有值的否定或零值事实，不是未知。每个事项只保留实际影响判断的待确认问题，不为所有可想象字段逐一创建疑点。

### 5.2 数量、金额与时间

| 内容 | 填写规则 |
| --- | --- |
| 绝对量与增减量 | “提高到2000次/分钟”是目标总量；“增加2000次/分钟”是增量；“目前1000”是现有量。不得互换。只在基准、对象、口径和单位全部一致且确定时计算差额，并标为计算结果；否则保留原话，目标或增量未知 |
| 数量单位 | 同时保留数值、单位、指标及适用对象。“2000”不能自行补次/分钟；TB/TiB、总量/日量、峰值/均值、并发/吞吐不混算；区间和约数保持原精度 |
| 金额与币种 | 同时注明金额用途、币种，以及已说明的含税/未税、单价/总价、计费单位、周期、一次性/经常性口径。币种未说不能因沟通语言推成人民币；报价、预算、合同金额、实付金额不能互相覆盖 |
| 时间语义 | 首次消息、最近相关消息、实际发生、目标期限、承诺时间、实际完成、确认时间分别表达；计划不写成已发生 |
| 相对时间 | 只有消息发送日期、时区和指向清楚时才解释“明天”等；原话和解释同时可核对。“尽快”“下周左右”不补成某日某时；只有日期时不补零点 |
| 不精确时间 | 只说“已完成”，能证明完成事实和不晚于该消息时已完成，不能补实际完成日期。“昨天恢复”可记相应日期或区间，不能补具体时刻；实际发生范围未知时保留未知 |

### 5.3 更新与撤销的共同规则

同一对象和语义下，有新证据才新增或更新；本轮未提及的旧事实不自动清空。新旧值先判断是否属于不同范围、单位、计划/实际或不同阶段，不能见数字不同就覆盖。明确更正只更正目标字段和相关标签；明确取消请求保留“曾提出、后取消”的事实，不能把曾经有效的请求伪装成从未发生。

最新发言不天然最可信。明确更正、已核实结果、适用时间及说话者对本事项的知情依据共同决定取舍；无法解开冲突时待核实。原证据被撤回或修订后，重审依赖它的标签、字段、摘要、身份判断和关系；旧版本保留为历史，不继续单独支撑现行结论。若唯一依据消失但并未明确证明事项从未发生，应标依据待核实；若明确说明原事项误报、并不存在，则作废原判断。

## 六、公共属性字典

表中的缺失规则、证据规则及更新规则与第五节共同适用。“事实组合”表示相关事实可合在一项表达，不要求再堆叠细碎字段。

| 业务名称 | 含义与值类别 | 何时可填 | 缺失表达 | 证据要求 | 更新/撤销规则 |
| --- | --- | --- | --- | --- | --- |
| 事项标识 | 用于持续认回同一事项的稳定标识 | 事项身份成立时 | 身份未明仅保留待确认线索 | 身份判断有对象、目标及对应依据；标识本身不是聊天事实 | 标签、标题、负责人或状态变化不换身份；拆分、并回或作废保留可追溯去向 |
| 客户归属 | 该事项服务的客户身份；标识或已确认名称 | 来源归属已确认 | 待核实 | 已确认的客户归属信息，不能靠群名猜客户 | 归属更正时核对全部关联；不把跨客户结果混为一个事项 |
| 标题与内容概述 | 对象、目标、事实及当前未完内容的简明业务表达；文本 | 最低事项依据成立 | 对象缺失则先待确认 | 只概括本事项的有证据内容；保留条件、否定及事实性质 | 新进展更新相关内容；更正旧结论；不得抹去仍存在的待办或复制另一事项事实 |
| 类型标签 | 六类及符合条件的其他；标签集合 | 每一标签达到第三、四节门槛 | 无可定标签时待分类 | 逐标签的原文片段及必要上下文 | 逐项增减并说明依据；不因未提及而删除，不因删除一标签丢弃仍成立的事项 |
| 对象与跟进目标 | 产品、环境、资源、交易或服务对象及本次应达结果；事实组合 | 对象可辨认，目标有直接表达 | 细节未知；身份疑点待核实 | 明确对象、回复指向或相互印证的上下文 | 名称纠正不换身份；若揭示独立对象或目标，重新判断拆分 |
| 消息首次时间（观察起始） | 当前可核对的最早有效相关消息时间；时间点 | 有有效消息证据 | 来源时间缺失则未知 | 消息发送时间，不是获知、整理或入库时间 | 补到更早有效消息可提前；移出无关证据或修订后重新核对 |
| 最近相关时间（观察结束） | 最新有效事实、请求或进展消息的发送时间；时间点 | 有直接相关新内容 | 未知 | 对应消息及其业务片段；纯收悉不延长 | 新有效证据可延长；迟到消息不把较新进展倒退；不代表已完成 |
| 实际发生时间/范围 | 本轮请求发生、故障影响、交易或流失动作实际发生的时间；时间点或区间 | 原文明确或可无歧义解释 | 未知；冲突待核实 | 说明发生时间的原文，区别于报告时间 | 迟报可补真实范围；不凭首次消息替代；计划时间不能填入 |
| 实际完成时间/范围 | 本事项约定结果实际完成的时间；时间点或区间 | 已有完成事实且说清何时完成 | 有完成但时间未说为未知；尚未完成为不适用 | 直接结果与时间依据；确认消息时间单独识别 | 撤销完成结论时撤销相应现行时间；不得改填最近消息时间 |
| 目标期限/承诺时间 | 客户期望或跟进方承诺的办理、交付、验证时间；时间事实组合 | 明确提出期望或作出承诺 | 未知；互相矛盾待核实 | 各自原文及承诺主体，标清期望还是承诺 | 变更留存前后范围及新依据；不由“尽快”补日期，不自动等于实际完成 |
| 事项跟进状态 | 本事项的责任和结果是否仍需跟进；原话及建议解释 | 有处理、等待、完成或取消等依据 | 未知；状态冲突待核实 | 状态事实、仍存待办及其对应对象；不是单个业务阶段词的机械替换 | 按第八节更新；完成、取消、作废分开；静默不关闭 |
| 主要跟进人员 | 明确认领或指派的主要责任人；人员或有角色区分的名单 | 有具体认领/指派事实 | 未知；明确未指派则记录该事实 | 明确认领/指派原话及可靠身份；参与、回复、被抄送不够 | 交接要有依据；本轮未提及不清空；明确撤销后移除当前责任，历史保留 |
| 事件等级 | 原文明确等级或依据已确认业务规则得出的等级；原话及依据 | 有明确等级，或有已确认规则及足够事实 | 未知/待评估；冲突待核实 | 原文及事实依据；“尽快”不推出P级 | 不自行创建官方枚举；新影响或有据更正后调整，保留旧判断 |
| 证据 | 支撑事项、标签、字段及变化的来源与原文片段；证据集合 | 已实际读到正文或注明来源的补充 | 不能核对的内容标未读/缺失，不作为事实证据 | 来源、消息标识、发送时间、对应版本、直接片段及支撑对象可核对 | 新增有效证据；旧版不伪装成现行；移出无关证据仍保留纠正理由 |
| 待确认问题 | 对成立、身份、分类、字段或轮次的具体疑点；问题及候选事实 | 存在影响当前判断的疑点 | 无实际疑点不填 | 写明冲突/缺失位置和所需澄清，不编候选事实 | 只在新增依据直接解决该问题时消除；不因其他字段更新整体清除 |
| 事项关系 | 延续以外的复发、前后承接或因果等具体关系；关系及理由 | 双方事项已可识别且关系有证据 | 关系不成立为不适用；可疑但未证实为待核实 | 直接引用或可核对共同对象和发生顺序；拆自同一条目不算依据 | 一方纠正时复核；不能把相关当同一；不复制前次全部事实给后次 |
| 其他的业务理由 | “其他”所代表的具体服务内容及排除六类的理由；文本 | 使用“其他”时 | 未用其他为不适用；理由不全不能确认该标签 | 按第四节证明真实事项、六类外内容及共存时的不可分目标 | 内容转为六类或拆分时重写/撤销；不得留下与现行标签矛盾的排除理由 |

## 七、六类专属属性字典

专属属性仅在所属事实适用且有依据时填写。一个事项有多个标签时可共享同一对象、数量或时间事实，但不能把一个标签的证据自动当另一个标签的证据。未提及的属性按第五节表达缺失，不能借空缺否定整个事项。

### 7.1 商机属性

| 业务名称 | 含义与值类别 | 何时可填 | 缺失表达 | 证据要求 | 更新/撤销规则 |
| --- | --- | --- | --- | --- | --- |
| 交易对象与采购范围 | 拟购/已购产品、服务、适用环境和范围；事实组合 | 范围已明确 | 未知；范围冲突待核实 | 本次交易原话，不借历史其他交易补齐 | 范围调整只改本次交易；独立采购批次分别判断 |
| 采购意向与评估事实 | 采购意向、购买评估、试用、方案、决策等事实；原话及性质 | 客户明确表达或有可核对转述 | 未知；转述未确认内容待核实 | 保留是否条件性、谁的意向、试用是否以购买为目的 | 取消购买是新事实；不抹去曾有商机；误把普通试用当购买评估则撤销该判断 |
| 计划规模 | 拟采购/迁入规模；带对象、数量、单位及绝对/增量语义的量 | 客户明确规模 | 未知；口径不明待核实 | 区分预计用量、采购量、资源配额 | 用量估算不能更新成已购规模；变更保留原计划 |
| 预算或交易金额 | 预算、报价、已确认交易金额；分用途金额 | 金额及用途有依据 | 未知；未成交的实际成交金额不适用 | 金额、币种、周期及已说明税费；不能把资源单价当总合同额 | 不同用途并存；明确更正相应用途，不覆盖成一个笼统金额 |
| 采购/上线计划时间 | 评估、采购或上线的计划时间；分语义时间 | 明确提及相应节点 | 未知；模糊时间保留原话 | 计划主体及对应目标；不以消息时间替代 | 延期更新相应计划；不转成实际购买时间 |
| 成交事实及范围 | 已接受、已签、已购买、已付等具体交易结果；事实组合 | 有对应直接结果 | 未证实成交为未知；明确仍在评估则成交事实未发生 | 分别证明签约、购买、付款及范围；“报价确认”不能代替成交 | 更正/撤销交易结果时逐项处理；资源交付不自动证明购买 |

### 7.2 流失属性

| 业务名称 | 含义与值类别 | 何时可填 | 缺失表达 | 证据要求 | 更新/撤销规则 |
| --- | --- | --- | --- | --- | --- |
| 流失对象与范围 | 涉及产品、用量、合同或合作部分；事实组合 | 范围明确 | 未知；不能扩大到全客户 | 直接对象及限定条件 | 新证据收窄或扩大时明确变更；不同对象独立跟进 |
| 风险、计划与实际变化 | 条件性离开、准备执行、已经执行等事实性质；原话及解释 | 有第三节要求的退出方向 | 未知；性质冲突待核实 | 原文时态、条件与行动；不得以强烈语气证明已执行 | 计划转实际需要执行证据；风险解除或计划取消不删除过去事实 |
| 原因与触发条件 | 客户说明的退出原因、条件或期限；文本/条件事实 | 明确说明原因或条件 | 未知；推测原因待核实 | 保留“若…则…”及原因来源；故障同现不等于因果 | 原因被排除则撤销该判断；不因此自动撤销仍成立的流失意向 |

## 八、跟进状态、业务结果与时间

### 8.1 事项跟进状态的建议用语

以下用语用于业务判断和验收，不代表既定官方枚举。原话与建议解释保留对应关系，无法判断时未知，不为填状态而编出“待处理”或“跟进中”。

| 建议用语 | 业务含义 | 足够依据与禁止跳转 |
| --- | --- | --- |
| 待处理 | 请求或问题已明确提出，尚无实际开始办理的事实 | 可由明确待办支持；“待处理”不等于没有负责人 |
| 跟进中 | 已有实际处理、核验、协调或推进动作，尚未达到整体结果 | 必须有动作事实；被人回复、纯收悉不足以证明开始办理 |
| 等待反馈/验证 | 当前推进受制于明确的答复、资料、交付或验证结果 | 指明实际在等什么；不因没有新消息推定在等待客户 |
| 已完成 | 本事项当前约定范围的跟进目标已达成，必要验证已完成，没有该范围内明确未完责任 | 必须有明确结果及对应范围；单个环节完成、静默、致谢、资源获批或上线均不足以自动证明整体完成 |
| 已取消 | 曾成立的请求、计划或办理责任被明确撤回或终止，不再继续当前目标 | 不等于从未存在；流失计划取消不代表客户实际流失；不续约的办理完成也不叫事项取消 |
| 已作废 | 原识别依据被明确纠正为误报、对象错误或事项不成立 | 保留原判断和更正；请求后来不做应是取消，不能作废真实历史 |

“待确认”单独表示判断疑点，可附着于任何上述状态或未知状态。例如事项正在处理，但金额冲突待核实；不能仅因一个字段待确认就否定已发生的处理动作。业务拒绝某请求并明确结束办理，可记录“请求被拒绝、办理结束”，不能写成请求目标已经交付；建议跟进状态是否完成，应以当时约定的答复/办理责任是否已结束判断并保留结果原话。

### 8.2 不用跟进状态替代各类事实

| 事实维度 | 可以表达的内容 | 不能据此推出的结论 |
| --- | --- | --- |
| 商机阶段及交易事实 | 意向、购买评估、试用、方案/报价、决策，以及接受、签约、购买、付款等具体结果 | 这些是非强制、可跳过或往返的业务描述，不是一条必须走完的官方阶段链；成交不证明后续交付完成，已结束跟进不证明成交 |
| 流失风险、计划、实际变化 | 条件性离开、明确准备或决定、已经减量/退出、风险解除或计划撤销 | 风险不等于事实；计划取消不抹去过去风险；流失已发生不证明挽留、交接或结算责任已经完成 |
| 故障恢复 | 指标、内部验证、客户确认分别对应的对象、范围及时间 | 指标恢复不等于客户影响消除，客户部分恢复不等于全量恢复，恢复不等于根因或报告等待办已完成 |
| 资源交付 | 请求、受理、获批、交付、可用验证及部分完成 | 批准不等于交付，交付不一定满足申请范围；内部扩容不证明客户有资源申请 |
| 功能验证 | 需求表达、答复、接受评估、承诺、上线及按条件验证 | 接收建议不等于承诺；上线不等于验收；正常阶段推进通常不换事项身份 |
| 商务办理 | 询价、报价、条款确认、签署、付款、到账、开票、退款等结果 | 出报价不等于成交，客户称已付不等于到账，已开票不等于款项结清；不同办理结果不得混写 |

多标签事项分别记录各方面事实。例如“配额已开通，报价仍待确认”，不能因资源交付完成而把该事项所有责任标完成；若本来具有独立办理目标，应按第四节拆分。客户只委托获取报价，报价答复已完成且无其他承诺时，商务事项可完成，购买事实仍未知。

### 8.3 时间与发生轮次

消息首次时间和最近相关时间表示**观察到沟通的范围**。实际发生时间和实际完成时间表示**业务发生的范围**。提出计划的消息时间、计划执行时间、实际执行时间以及确认消息时间可以不同；任何一个都不能默认代替另一个。确认消息时间也不自动是业务完成时间。

例：11月12日10:00发言“11月10日20:00已交付，11日验证通过”。消息首次时间以实际已知相关消息确定，最近相关时间可为12日10:00；交付实际时间为10日20:00，验证日期为11日，整体完成时间需按本事项约定结果判断，不能直接填12日10:00。若只说“已经交付”，交付事实成立，实际交付日期未知。

恢复边界也须分清“何时恢复”和“何时确认恢复”。内部核验只能证明其所测范围，已确认身份的客户本人或明确授权代表的确认才能记为客户确认；不能把二者互相冒充。**识别独立新轮次不统一要求前一轮客户本人确认完成。** 明确的新影响窗口或独立结果已足以成立时，可以建立新轮次；要断言“恢复后复发”，必须有可信的前次相应范围恢复事实及后次重新发生证据。若只有“又不行了”、没有可核对的前后边界，应待确认，不默认持续、恢复或复发。

实际发生在恢复前的迟到日志属于前次补充，不能因现在才收到而认定复发。明确更正“之前测错，实际上从未恢复”应撤销相应恢复事实并继续原事项；若此前已错误拆出新轮次，应复核并回或更正关系，不留下两项重复跟进同一轮问题。

## 九、证据与自动更新规则

### 9.1 逐标签、逐字段的直接依据

每个已采用的标签和有值属性，分别列出能直接证明该判断的原文片段及必要上下文。支持事项存在的整条消息，不自动证明其中所有标签和字段。多个标签可引用同一片段，但必须能分别满足各类门槛；多个字段可共享证据，不必为每个字段虚构不同出处。

对象靠上下文补足时，同时保留新增片段与被指向的依据。引用、转述和新增发言分开理解：“客户说已付款”支持客户付款陈述，不证明财务已核实到账；历史摘要或旧标签只能作为查找线索，不能替代源事实。

原文、解释、已验证结果要清楚区分。不从“故障后扩容有效”推导“根因为容量不足”，不从“谢谢”推出“客户验收通过”，不从某人多次回复推负责人，不从金额相同推出同一合同，不把系统整理或处理成功当业务事项完成。

### 9.2 变化情形

| 情形 | 应如何处理 |
| --- | --- |
| 同条消息多事项 | 按对象、目标和发生轮次分片；各片段可以支持各自事项，同一消息也可同时有非事件和待确认片段；不为避免重复引用而漏掉真实事项 |
| 否定 | 先确定否定对象、范围和时间。“没说要采购”否定商机依据，不否定其明确提额请求；“还没恢复”不能识别为恢复 |
| 条件或假设 | 有现实对象的条件性流失、条件性采购或功能请求，按条件事实记录；纯示例或无现实指向的假设不建事项；不把条件满足前的结果写成事实 |
| 撤销 | 区分撤回真实请求、取消计划、撤销错误结论及删除消息。撤回请求保留历史并取消对应目标；标签仍可说明曾存在的真实请求，不代表仍在办理；只有标签原依据错误、不再支持或已被重新归类时才移除标签。删除消息不单独证明原事实虚假 |
| 明确更正 | 根据更正目标重新检查对应标签、字段、摘要、时间、身份和关系；只改有影响的部分，不丢仍成立的其他业务内容 |
| 相互冲突 | 保留来源、适用范围和候选结论，标具体字段待核实；未经澄清不按最后发言、职位猜测或多数意见自动决定 |
| 迟到消息 | 按其业务时间和内容定位；补历史事实，必要时提前观察起始或补实际范围；不得把更晚的现状倒退，也不能只因迟到而忽略对旧错误的明确纠正 |
| 消息修订 | 新旧正文分别可追溯；复核旧版本支撑的全部判断，撤销不再成立的依据；另有有效独立证据时保留其可支持范围。不能把新版没有的旧引文当现行证据，也不能仅标“已修订”便声称全部复核完成 |
| 重复或收悉 | 无新事实不新建，不延长业务发生/完成时间；“今天仍失败”是新的状态确认，有业务意义，不因字面重复丢弃 |
| 图片和附件未读 | 占位、文件名、链接仅证明存在该附件，不证明内容；正文已清楚的事项可成立，未读部分独立保留疑点；不能声称从图中识别出错误码、金额、根因或完成结果 |

### 9.3 自动复核与更新

事项识别、类型判断、字段提取和后续更新由系统自动完成。字段未提及或证据不足时保留未知，不影响事项成立和其他字段处理。多个仍有效的直接依据相互冲突，或对象、目标、发生轮次存在会改变归属结果且现有证据无法消歧时，只将受影响字段或关系标为待核对，并记录冲突点及缺少的证据。不得把待核对作为常规分流，也不得为减少待核对而强行拆分或合并。

新消息出现时，系统结合当前原文、可用历史证据、事项身份和消息版本重新判断。明确更正只更新其直接指向的事实；没有新依据时保留既有判断和未知状态；来源版本失效时复核所有受影响的标签、字段、摘要及事项关系。标签变化不改变事项身份。

## 十、业务验收清单

按具体业务片段核对，不能只看消息是否被分到某处。每项验收都应能给出采用或不采用的结论及依据。

- 最低依据：真实指向、对象、具体目标/问题/结果齐备；资料不全的真实事项没有因缺数量、负责人、根因、日期或等级被漏掉。
- 六类边界：每个标签满足本类最低证据，普通询价未被升级为采购，试用未被写成购买，抱怨未被写成流失，内部措施未被写成客户资源/功能诉求。
- 功能与性能：已有功能改善可以成立功能需求；恢复既有预期、现有资源交付和新增表现目标已经区分；未知方案没有被补成根因。
- 咨询：已形成具体答复、核验或服务责任的咨询能成立事项；泛泛问答、纯收悉、未读和待确认没有被混为无事件。
- 标签与边界：同一事项多标签没有重复建项；独立对象、目标、轮次及验收结果没有被误合；正常阶段推进没有被机械拆开。
- 其他与待分类：每个“其他”都有真实事项依据、具体内容和排除六类理由；共存时说明额外内容及不可分目标；证据不足没有被当六类外事实。
- 属性：每个有值字段有直接依据；原话与解释、转述与核实、请求与结果、总量与增量、金额用途及币种、数量单位、计划与实际时间没有混写；未知、不适用、待核实可区分。
- 状态和时间：跟进状态与各类事实分开；完成有本事项范围的结果依据；最近消息、入库/整理、确认时间没有代替实际完成；静默和致谢没有关闭事项。
- 连续性：跨天、跨群、同义表达及换人可认回；复发、新独立批次和更正恢复分开；没有固定时间切分或同群即同一的判断。
- 变化：否定、撤销、更正、冲突、迟到和消息修订影响到的标签、字段、时间及关系都已核对；没有把未提及的旧值清空，或把旧版本继续当现行依据。
- 附件：未读图片不产生正文事实；部分已读内容不会被附件未读一并丢弃。
- 判例：附录各例的建项、标签、属性、合并拆分及理由互相一致；一个事项可共享消息片段，但无关话题没有借证据混入。

## 十一、待业务裁定的少量问题及建议

| 问题 | 当前建议口径 | 裁定前如何继续判断 |
| --- | --- | --- |
| 跟进状态及等级最终取值 | 跟进状态可采用第八节业务含义；等级仍只用已明确原话或已确认的业务规则，不从语气或未确认评分规则推定 | 记录已知事实、原话及未知项；不把建议用语称为官方要求，不影响事项识别 |
| 哪些结果需要客户验收，谁能代表客户确认 | 依据具体事项的约定验收责任；未约定时，内部结果只证明内部所测范围，客户本人或明确授权代表确认才称客户验收 | 记录主体和范围；整体完成的必要验证不明时待确认，但独立新轮次不被前次未正式关闭阻塞 |
| 六类之外的服务边界及“其他”共存 | 按第四节严格使用；专项培训、具体适用性核验等确有独立服务责任时可为其他；与六类共存限有证据的不可分服务目标 | 保留具体服务内容及排除理由；能独立验收就拆分；无法排除六类则待分类，不扩展新主分类 |

## 附录A：合成边界判例

以下均为自造业务内容；示例人物、对象和编号只用于区分事项。未说明的负责人、根因、等级、金额、币种及实际日期均不补填。“建”表示事项依据成立，若已存在同一事项则更新；“待确认线索”不表示已确认具体事项身份。

| 编号 | 输入短句或必要上下文 | 应否建事项与标签 | 关键属性或缺失 | 合并拆分/延续判断及理由 |
| --- | --- | --- | --- | --- |
| A01 | “早上好，收到，谢谢。” | 不建；无标签 | 无完成、恢复或验收事实 | 即使上下文有故障也不据此关闭；纯收悉不增加实质进展 |
| A02 | “A服务按月怎么计费？请给现行报价。”没有采购表达 | 建；商务需求 | 办理目标为价格答复；购买意向、报价金额和币种未知 | 同次询价的催答和出价延续；不能标商机或成交 |
| A03 | “我们决定为A项目新增采购B服务，请报一年方案价。” | 建；商机、商务需求 | 采购对象、期限一年；预算、成交和付款未知 | 同一采购报价目标用一项多标签；询价不拆成重复事项 |
| A04 | “先给A环境开个试用配额，测试一下是否合适。”未说明购买评估 | 建；资源需求 | 试用开通请求；额度、期限和商业目的未知 | 具体技术试用可跟进；不能因“试用”直接标商机 |
| A05 | “准备购买B服务，先开试用配额验证采购方案。” | 建；商机、资源需求 | 购买评估和试用交付请求；购买结果未知 | 同一购买评估目标多标签；试用成功也不能自动写已购买 |
| A06 | “订单P已确认购买B服务，款已由我们支付。” | 建；商机、商务需求 | 购买事实、客户付款陈述；到账核实、币种、金额和实际付款日期未知 | 若订单P已有采购事项则更新；不能另建一条同一订单的“成交事件” |
| A07 | A下载故障处理中，支持方说“我把后端节点扩了，继续观察。” | 更新原事项；排障 | 已执行内部扩容；根因、客户恢复和客户资源申请未知 | 故障处置延续；不加资源需求、商机或功能需求 |
| A08 | “请提高A环境配额，具体数值还在测算。” | 建；资源需求 | 资源对象和申请动作明确；目标量、增量、交付时间未知 | 不能因未给数量拒绝建项；后续给量更新同一申请 |
| A09 | “A现有1000次/分钟，请提到2000。”后更正“不是提到2000，是再加2000。” | 建并更正；资源需求 | 当前基准1000，最终请求增量2000次/分钟；目标3000仅可注明为同口径计算 | 同一申请不换身份；保留原总量口径及更正，不能把增量2000当目标总量 |
| A10 | “什么叫并发？只是学习概念，暂时没有业务要处理。” | 不建；无标签 | 无现实业务核验或交付责任 | 普通知识讨论不以其他兜底；与具体上线核验区分 |
| A11 | “A项目上线前请按这份使用条件核验现有B服务适不适用，给我们书面结论。”仅委托适用性核验 | 建；其他 | 服务目标为具体适用性核验答复；结论未知 | 咨询已成为服务；目标不含采购/退出、异常、资源交付、产品改变或商务办理，符合六类外服务，不能机械排除“咨询” |
| A12 | “A导出支持取消吗？若还不支持，请增加取消任务能力，避免长任务误跑。” | 建；功能需求 | 条件性功能请求和场景明确；当前是否支持待核实 | 请求内容明确，不只是询问现状；若后续证明已支持且无新目标，按澄清结束答复或更正需求判断 |
| A13 | “A导出目前正常，但想把多步操作合成一键，请改善。” | 建；功能需求 | 当前正常、期望一键行为；承诺、验收指标未知 | 已有功能改善可成立；不因“优化现有功能”排除，也不标排障 |
| A14 | “A导出原来能取消，今天取消按钮失效，请恢复。” | 建；排障 | 既有预期和异常明确；根因未知 | 恢复已有行为，不因需改程序标功能需求；后续修复和复测延续 |
| A15 | “A接口平时200毫秒，今天同样请求要5秒，请排查。” | 建；排障 | 基线与退化有客户报告；原因、容量缺口、影响人数未知 | 性能异常不直接等于容量申请或新性能需求 |
| A16 | “现在性能符合约定，为活动请换到现有大规格实例，以满足更高吞吐。” | 建；资源需求 | 现有规格交付请求；目标吞吐数量未知 | 无异常或产品能力变化证据，不加排障或功能；规格交付与验证延续 |
| A17 | “现有搜索功能符合标准，但希望产品在同样资源条件下支持10万条实时检索，目前没有这项能力。” | 建；功能需求 | 新能力及同资源条件明确；实现方案、承诺未知 | 性能/规模改善也可为功能目标；未请求交付资源，不标资源需求 |
| A18 | “A导出今天又失败了，你们服务太差。”上下文能认回仍未恢复的同轮故障 | 更新；排障 | 新一次失败确认；流失意向未知 | 抱怨不等于离开；“今天仍失败”有新事实，不能当纯重复忽略 |
| A19 | A故障未解，客户说“本次再不恢复，我们就把A业务迁走。” | 更新；排障、流失 | 流失为条件性风险，条件为未恢复；实际迁移未知 | 仍围绕同一恢复目标可多标签；不能写已经流失 |
| A20 | “A业务昨天已迁走30%，余下继续留在这里。” | 建或更新对应流失事项；流失 | 实际迁移30%、范围为A；基准量、去向未知；昨天按明确发送日期解释 | 不扩大为整家客户流失；若为A19风险兑现则延续，独立迁移执行目标另判断 |
| A21 | “合同C下月续费，请发续费合同办理。” | 建；商务需求 | 正常续费手续；具体签署、付款、到期日未知 | 没有退出方向，不加流失；“下月”不补某一天 |
| A22 | “合同C决定不续约，请办理本期到期终止手续。” | 建；流失、商务需求 | 不续约计划及终止办理请求；实际终止、具体到期日未知 | 同期合同目标可多标签；决定不续约不能写成已终止，办理后记录对应结果 |
| A23 | “请为现有A产品安排一次专项使用培训，以完成约定讲解为结果。”不涉及新采购或其他六类内容 | 建；其他 | 培训对象和服务结果；时间、责任人未知 | 排除采购、流失、异常、资源、新能力及商务办理；培训不是新主类型 |
| A24 | 申请R可确认是同一待办：“A项目申请R的交付请继续办理。”现有材料未说明交付是配额、功能、报价还是专项服务 | 保留事项待分类；无确认标签 | 申请R及交付待办可定位；类型及交付细节待核实 | 证据不足以排除六类，不能标其他；后续澄清更新同一R |
| A25 | “请办一次A实操培训，并按本次服务约定为学员开只在现场使用的临时实验配额；只验收同一场带配额实操，无单独开通目标。” | 建；其他、资源需求 | 培训义务及临时配额交付分别有证据；配额量和时间未知 | 其他只代表六类外专项培训；客户明确不可分服务目标，满足共存；若另有独立开通验收则应拆分 |
| A26 | 同一句：“给A环境提额；另请B控制台增加批量导出；合同C的发票也请催办。” | 建三项；分别资源需求、功能需求、商务需求 | A量未知；B预期行为明确；C发票办理结果未知 | 对象、目标及结果独立；同消息分片引用，不把三标签堆成一个大事项 |
| A27 | 原话“付费增购A配额并报价”；后明确更正“刚才采购和报价说错，本次只申请原权益内提额，没有采购报价请求。” | 原事项保留；移除商机、商务需求，保留资源需求 | 原商机和报价依据被明确纠正；额度仍未知 | 标签移除不换身份；若只是后来取消真实采购，应保留曾有采购及取消事实，而非按误述删除 |
| A28 | 11月1日报A下载故障，11月10日换人说“工单T那次A下载一直没好，继续排查。” | 更新原事项；排障 | 明确同对象、工单与持续未恢复；根因未知 | 跨天、空档和换人不新建；不能按固定天数关闭后再建 |
| A29 | 前次客户确认“A上传已恢复”，后说“恢复后今天A上传重新失败，是新的一次。” | 建新轮次；排障 | 前次恢复与本次重新发生分别有证据；本次根因未知 | 记录复发关系，前次保持原事实；不将新故障塞回旧轮次 |
