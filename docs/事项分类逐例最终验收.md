# 事项分类逐例最终验收

验收日期：2026-11-17。范围为第六阶段实际实现与合成回放；本报告不修改执行跟踪文档，也不代替主会话独立验收。

## 1. 方法、假设与判定范围

本轮假设：规范 A01–A35 的原始短句是输入；同一事项的后续句按窗口依次处理。固定 FieldsProvider 负责提供 schema 5.0 的明确判断，程序负责验证合约、归属、采用决定、保存、版本和 HTTP 查询。全程未调用真实模型、上游取数或业务数据库，未读取业务 `.env`、实际聊天及客户数据。固定输出通过不等于自然语言分类准确率通过。

分三步实施：先把原句与分支送入正式增量入口并复现失败；只修复阻断验收的直接缺口；最后运行定向、完整非 MySQL、前端和最终源码隔离 MySQL。每一步分别核对业务结果、历史不变、接口及事务。无新增依赖、业务表、自动合并入口或通用依赖传播引擎。

`backend/tests/final_replay.py` 复用实际 `IncrementalService`、正式归属和字段执行，使用合成内存仓库、固定 Provider 及无监听的 HTTP TestClient。查询使用实际 `QueryService` 的筛选与证据富化。每轮检查：

- 事项数量、稳定 ID、完整标签集合、当前摘要、采用字段、扁平与类型投影一致性。
- 八种标签筛选及事件详情 HTTP 结果；缺省等级保持未知、无依据的负责人保持空。
- 每条字段和标签引文来自其保存的消息 digest，时间来自该版本 `send_time`。
- 既有修订逐条保持不变，指定旧周期返回旧快照。

测试数据的业务时间统一为合成的 2038 年；不将当前机器日期代入合成对话。

## 3. 八组旧依据修订反例及独立有效依据对照

`test_evidence_revision.py` 共 20 项。每组均先保存旧版本，再提交相同消息 ID 的不同 digest；独立对照来自另一消息，不能把编辑后的正文重新绑定为旧引文依据。

| 组别 | 无独立有效依据时 | 存在独立有效依据时 |
| --- | --- | --- |
| R1 采购报价改为原权益内提额 | 明确纠正后移除商机、商务标签及当前属性；原资源事项 ID 不变 | 独立采购报价依据保留对应标签；旧编辑版本单独标失效，不清空有效支持 |
| R2 报障正文消失／明确误报 | 变成文件时仍保留待核对事项，标签与摘要提示失效；明确误报时按有据更正撤销排障并标原误报作废 | 独立报障依据仍在，不把整项标签一并撤掉；旧依据标失效，无错误的“唯一依据消失”疑点 |
| R3 增量依赖的原基准变化 | 原基准 1000 改 1500；旧计算增量 1000 标失效并待核对，旧 digest 保留，不自动重算或重绑 | 独立消息仍支持的事实不连带清除，不补新算术结果 |
| R4 迁走 30% 改为剩 30%、迁走 70% | 有据更正采用 70%，相关失效疑点解决，旧快照为 30% | 独立 30% 仍有效时保留采用值，新 70% 作为冲突待核对 |
| R5 恢复及完成更正 | 首先实际保存完成状态和非空关闭锚点；明确纠正后撤恢复，采用“正在排查”，关闭锚点清空 | 独立恢复和完成确认仍在时不误清恢复/完成；原恢复更正转待核对 |
| R6 已付款改为准备付款 | 只纠正付款陈述，原“报价答复已完成”保留；旧付款版本保留历史 | 独立付款依据仍在时保留采用付款事实，准备付款成为冲突建议 |
| R7 复发所依赖的前次恢复消失 | 前次恢复依据变为未读文件后，子项复发关系待核对，旧关联快照不变 | 独立恢复确认可继续支撑前次恢复和子项关系，不错判为全部失效 |
| R8 因果消息消失／明确撤回 | 消失时关系 pending；明确撤回时 retracted；两个独立事项及其标签保持 | 独立因果消息仍有效时保持 confirmed，失效的单条依据仍单独标识 |

R3 只验证直接保存的计算事实失去依据时可被发现；不验证一般公式解析、单位换算、多跳派生传播或重算。R2/R8 的独立对照验证保留有效支持，不将固定 Provider 未输出的新纠正语义冒充程序已自动理解。

复核发生在已加载客户事项和本轮消息版本内，支持 Provider 返回空候选。没有实现扫描其他客户或任意外部依赖图的传播。

### 直接依据版本恢复的补充回归

主会话独立复验发现：同一消息从 v1 改成未读内容 v2，再恢复完全相同的 v1/digest 后，旧实现仍永久保留 superseded、两个字段疑点和摘要待核对。新增回归首次 7 failed、1 passed；本组共 8 项。

修复按当前可验证消息版本重新判断每条引用是否现行，再分别更新字段/标签依据状态、摘要提示和本轮负责的版本疑点。保留旧修订不变；没有重新采用已撤销标签、已更正事实或已撤销关系。

正式增量回归覆盖 v1→无可读内容→原 v1、普通不等价 v3 不恢复、仅解决一个来源的版本疑点而保留另一来源失效/互斥问题、已更正事实、恢复及复发依据往返、关系往返及明确撤销不复活。实库用例也补入关系依据原版本恢复后的状态、旧快照和收据核对。

## 4. 可信恢复范围的合约补齐

按规范 8.3 补充 4 项实际正式链路测试。原合约固定客户账号恢复，首次运行 4 failed，合法的支持方范围核验在解析层被拒绝。现在新增 `verify_recovery` 和可核对的 `scope`：

1. 仅明确配置为 internal 的支持账号可建立支持方核验；身份未知仍 review。
2. 原文明确只测 A 上传测试环境、生产未测、客户未验收，保存身份依据 `confirmed_support_account`、原引文版本和测试范围；不自动关闭工单。
3. 同一测试范围在确实恢复后出现明确的新影响窗口，可独立新建并关联前次；不统一要求客户本人先验收完成。
4. 全环境复发不能借用仅测试环境的恢复；无范围和边界的“又不行了”保持待确认。

历史候选输入携带恢复身份、范围和核实状态，避免模型看不到合约所需边界。前端把支持方核验明确显示为“客户验收未确认”，待核实恢复与复发不再显示成已确认。

范围采用引文原话及精确一致校验；尚未实现范围包含关系、语义同义归一、多份不同范围核验的集合推导。支持方核验和客户验收采用不同事实身份，后续身份或范围不同的确认先进入 review，不静默扩大原边界。

## 5. 修复及保留的实现边界

本轮直接修复：新增加标签时属性被提前归档；省略主语的原始后续句无法检索到近期同会话候选；空候选下不复核旧依据；部分有效支持被整体清除或更正后疑点不解决；恢复/复发及明确事项关系缺少失效状态；支持方可信范围核验被合约拒绝；页面将待核实恢复误显为已确认。

近期同会话只是有预算的候选检索线索，正式归属仍要求新旧依据。独立方案承接/因果关系保存在现有 Event JSON；校验目标属于输入、直接引文、旧事项依据、未来时间、自引用、重复和循环。新增关系负例覆盖无目标、无旧依据、错引、自引用、重复、三项循环和同批循环；失败时事务回滚。

复核标识旧 proof 失效，保留旧 digest，不改旧修订。仍有独立依据时保留采用值；唯一依据消失时保持原记录并显式待核对，不能自动猜新标签、摘要或身份。已明确纠正的事实按已有字段流程处理，新标签和类型属性按当前直接证据自动更新。

当前摘要中仍出现、且没有其他有效支持的旧变化片段，会显示“概述依据已修订，当前表述待核对”；程序不自行重写任意自然语言概述。新引文失效状态通过 API 保留，字段详情和恢复/关系详情将旧引文标为仅供历史核对。

### A30 已误拆身份的精确缺口及最小后续方案

实际流程先保存恢复、再建第二发生轮次，然后提交“测试错环境、一直没恢复、两条其实同一次”的更正。结果是原项恢复撤销、子项复发关系 pending，两个 ID 和旧快照均在，默认查询仍返回两项。当前自动身份流程不能表达已误拆事项的身份归并。这个分支未完成，不能用通过的“单身份更正”替代验收。

最小后续入口需要在既有客户事务/锁中提交：保留的主 ID、被并入 ID、两者预期版本、幂等操作 ID、操作人审计标签、理由及明确归并依据。只允许同客户同分析流且非自身；提交前完整核对版本及依据，不可用同群、同标签或时间接近自动归并。

建议在现有 JSON 保存可查询的 `merged_into` 与归并审计修订；默认列表及计数只跟踪主身份，直接访问被并入 ID 时返回明确的主身份定位。旧 ID、原证据、旧快照和既有收据保持可追溯；主项补入有据的同轮证据，字段冲突沿用待核对规则。失效的复发关系须在归并修订中明确撤销；指向其他事项的有据关系需要逐条核对，不应自动重写整个图。需覆盖旧版本冲突、幂等重放、回滚、历史/收据查询及默认计数。这是最小方案说明，本阶段未增加该接口、实现或业务表。
