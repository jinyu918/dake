# 群识别与消息过滤开发方案

日期：2026-11-17。状态：待实现；本次更新实施口径。

本任务在已有增量流程中增加配置化群识别与消息过滤。客户群和客户内部协作群正常参与事件分析；MaaS 供应商群按已确认的名称规则排除，CDN 供应商群及内部产品群按明确清单排除。原始消息继续保留，过滤决定必须可追溯。

业务口径来自本次会议及用户后续确认；配置格式、默认行为和接入方式是本开发方案的工程设计，不是官方事件分类标准。其余约束继续遵循 [项目简报](项目简报.md) 和 [工程架构](工程架构.md)。

全量群发现、缺失 UID 的关键词补查和大客户准入见 [多客户接入与定时增量开发方案](多客户接入与定时增量开发方案.md)。本方案中未知群用途默认保留，不代表缺少客户 UID 的群可以进入分析；客户归属仍待确认时先不处理。

## 已确认的范围

| 群范围 | 识别方式 | 分析策略 |
| --- | --- | --- |
| 客户内部协作群 | 群名中的已确认“内部”标记，或明确群 ID 配置 | 保留，可发起事件、补充进展 |
| 客户群 | 明确群 ID 配置或后续权威群类型字段 | 保留 |
| MaaS 供应商群 | 已确认的“供应商”名称规则 | 排除 |
| CDN 供应商群 | 可列举的群 ID 清单 | 排除 |
| 内部产品群 | 可列举的群 ID 清单 | 排除 |
| 未识别群 | 没有命中明确规则 | 标为待确认，默认保留，不自动判为客户群 |

当前官方样例客户返回的三个群，已确认是两个内部群和一个客户群，全部保留。第三个群不能因为名称含产品或 AI 字样就被排除；内部产品群必须命中明确清单。真实群名、群 ID 与身份映射只放在私有配置，不写入本文或测试夹具。

“内部群”是保留范围，“内部产品群”是明确列举的排除范围。名称识别使用完整配置词，例如“内部”，不使用单个“内”字匹配任意群名。

2026-11-17 用户明确：需要跨群合并，沿用现有同客户跨群归属能力，不再将“暂不跨群合并”列为待确认限制。现有增量服务按 UID 汇集多群消息和历史事件；基础匹配按类型、主题与时间判断，不要求群 ID 相同，正式归属流程可更新同客户的已有事件。后续在此基础上集成并验证跨群场景，不把现有能力列为从零开发，也不将不同客户或不同事项自动合并。

## 现有实现与缺口

`ingestion/adapter.py` 将接口的分群记录归一，并按 `send_time` 全局排序。群字段包括 `group_number`、`group_name`、`records`、`total`，当前缓存没有明确的群类型字段。消息的 `is_inner` 保留为提示值，不用于推断群用途。

`services/processing.py` 按 UID 和分析流读取待处理消息、上下文与历史事件。已有 `sender_kinds.py` 区分已确认的机器人和人工账号，但没有供应商群、内部产品群过滤。

群用途与发送者身份是两套规则：群允许分析后，再执行既有机器人规则；机器人过滤不能代替群过滤。

## 本轮排除清单口径

2026-11-17 用户明确：先预留排除清单配置入口，初始清单为空，不以提供实际群清单作为开发或上线前置条件。不得自行填入真实群、猜测排除对象，或把下文合成示例当作实际配置。名称规则与精确群清单仍是独立配置项，不因预留清单而自动新增或启用名称排除规则；下文描述的是配置相应规则后的行为。

## 配置与规则优先级

新增私有配置文件 `data/config/conversation_policy.json`，从项目根目录解析，不随启动目录变化。第一版使用本地文件，不新增设置页面或数据库表。

配置按客户 UID 和消息来源隔离。明确群配置使用 `conversation_id`，对应官方接口的 `group_number`；群名仅用于名称规则和本地展示。禁止根据群名中的数字自行改写所属 UID。

匹配顺序如下：

1. 精确群 ID 排除清单，包括供应商群和内部产品群。
2. 当前客户范围内的供应商名称排除规则。
3. 精确群 ID 保留分类，包括客户群和客户内部协作群。
4. 当前客户范围内的“内部”名称规则，识别为内部协作群并保留。
5. 未命中时返回未知、待确认，按配置的默认策略保留。

排除规则优先，不能被普通内部群规则或保留分类覆盖。多个排除原因同时命中时全部记录；同一群 ID 被重复定义为不同用途时，配置校验失败，要求维护人纠正，不静默选择其中一项。

以下配置全部使用合成标识；字段名称为拟议接口：

```json
{
  "schema_version": 1,
  "enabled": true,
  "unknown_action": "include",
  "scopes": [
    {
      "uid": "synthetic-customer",
      "source": "official_chat",
      "groups": [
        {
          "conversation_id": "synthetic-customer-group",
          "kind": "customer",
          "basis": "群维护人确认"
        },
        {
          "conversation_id": "synthetic-internal-group",
          "kind": "internal_service",
          "basis": "群维护人确认"
        },
        {
          "conversation_id": "synthetic-product-group",
          "kind": "internal_product",
          "basis": "已确认的内部产品群清单"
        },
        {
          "conversation_id": "synthetic-cdn-group",
          "kind": "supplier_cdn",
          "basis": "已确认的 CDN 供应商群清单"
        }
      ],
      "name_rules": [
        {
          "rule_id": "supplier-name",
          "contains": "供应商",
          "kind": "supplier",
          "basis": "已确认的供应商群命名规则"
        },
        {
          "rule_id": "internal-name",
          "contains": "内部",
          "kind": "internal_service",
          "basis": "已确认的内部群命名规则"
        }
      ]
    }
  ]
}
```

`kind` 是技术群用途，不替代官方六类事件。`supplier`、`supplier_cdn`、`internal_product` 对应排除；`customer`、`internal_service` 对应保留。第一版名称规则仅支持非空字符串包含匹配，不执行任意正则或脚本，不根据未命中“内部”就认定为客户群。

缺少文件或 `enabled=false` 时兼容现有行为，全部保留并标记过滤未启用。启用后，未知枚举、空匹配词、重复范围、冲突群定义、缺少确认依据或损坏 JSON 均明确报错；任务不能静默退回不过滤。本轮排除清单初始为空，后续需要排除时再维护私有配置，代码不内置样例客户的真实身份数据。

## 接入业务流程

新增 `services/conversation_policy.py`，集中实现配置校验、规则匹配、配置指纹和只读判断结果。适配器继续只负责归一；CLI、API 和后台任务复用同一业务流程，不各写一套过滤逻辑。

一次执行按以下顺序处理：

1. 冻结本次群规则，记录规则实现版本及配置指纹。
2. 正常取数、归一和消息 upsert，保留原始响应及消息。
3. 对待处理消息做群判断，拆为允许分析和已排除两组。
4. 仅对允许分析的消息执行机器人识别、历史检索和模型抽取。
5. 按现有合约校验候选、匹配及更新事件，拒绝引用被排除群的新证据。
6. 将事件更新、消息处理标记与执行收据按现有事务边界提交，并保存过滤审计。

只有排除消息的窗口不调用模型，不创建或更新事件，但要保存本轮处理结果及被排除消息的处理标记，避免重跑时反复处理。消息处理标记代表本策略下已处置，不等于送入模型分析；不能将过滤决定改写进原消息 digest。

过滤必须覆盖新增消息、常规回溯上下文、机器人辅助消息、历史证据补取和同群邻域读取。被排除消息不能通过另一个背景入口重新进入模型。所有候选的证据校验也要使用相同规则。

历史事件的概述可能已经包含被排除群的信息，不能仅去掉当前聊天就宣称输入已完全过滤。上线前检查存量事件来源；存在混合来源或来源不足时，必须明确处理范围和迁移方案。可在显式指定的新分析版本中按新规则逐窗口重放，旧结果保留；不得自动删除旧事件、改写旧概述或触发全量重洗。

## 配置冻结与审计

网页任务提交时冻结群规则；整次回放沿用同一份规则，CLI 回放采用相同方式。排队或执行中修改文件只影响新任务。重试和展示恢复使用原执行规则，不悄悄换用新配置。实现时将规则快照接入现有任务与执行元数据，不另建并行任务系统。

规则实现版本和配置指纹应参与分析策略身份及幂等设计，防止旧策略的处理标记错误阻止新策略处理。新配置不等于自动重洗授权：切换分析版本、查询范围与回放范围必须显式指定，网页仍能分清旧结果和新结果。

每条过滤审计至少保存：消息键、群 ID、判定用途、是否允许分析、命中规则 ID 或清单依据、规则版本、配置指纹。审计写入现有执行／周期记录，沿用失败与恢复机制；过滤原因只描述规则，不复制群名或聊天正文到普通日志。

统计至少区分本轮待处理数、按群排除数、允许进入后续分析的数量；允许进入后续分析的消息还可能被机器人策略处理，不能直接将其计为模型输入量。

群过滤控制事件分析，不作为聊天访问权限机制。旧事件和其原始证据不因规则变更而消失，页面应能识别其所属分析版本。若新增页面字段，按现有 OpenAPI 流程生成客户端，禁止手改生成文件。

## 验收场景

测试全部使用合成消息、群 ID 和群名，不把真实配置写入断言。

| 场景 | 预期结果 |
| --- | --- |
| 初始排除清单为空且没有启用名称排除规则 | 不产生群排除，保持现有分析行为 |
| 同一客户同一事项来自不同群 | 可关联并更新同一事件 ID；不同事项不因同客户而强制合并 |
| 两个普通内部群和一个客户群 | 全部保留，内部群可独立发起事件 |
| 群名含“内部”和“AI”，未命中排除清单 | 正常保留 |
| 内部产品群同时带“内部”标记 | 清单排除优先，不进入模型 |
| 群名同时含“供应商”和“内部” | 供应商排除优先 |
| CDN 供应商群没有供应商名称标记 | 按群 ID 清单排除 |
| 不同 UID 或来源出现相同群 ID | 不串用其他范围配置 |
| 未知群或空群名 | 明确待确认，默认保留 |
| 排除群消息出现在回溯、邻域或机器人辅助输入 | 同样排除，不能回流到模型 |
| 候选引用被排除群消息 | 校验拒绝，不能落事件 |
| 一个窗口全部被排除 | 不调模型、不生成事件，处理标记与审计完整 |
| 同窗口重跑、事务回滚或提交后展示失败 | 沿用既有幂等与恢复保证，不漏标或重复更新 |
| 任务执行中配置被修改 | 当前任务沿用冻结配置，新任务使用新配置 |
| 配置损坏或冲突 | 明确失败，不伪装处理完成 |
| 过滤启用前的事件已有排除群内容 | 不直接当作已净化历史输入，先落实迁移方案 |
