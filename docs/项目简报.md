## 1. 项目是做什么的

这是七牛云技术支持部的内部项目，工作名称是「大客售后智能系统」（会议转写里出现的「阿克售后」是误听，事件类型里的「牌照」应为「排障」）。

业务目的：从大客户售后过程中的多源信息里，自动识别出真正要跟的事件，让不同角色看到该看的内容，减少漏跟和重复劳动，并给后续日报周报、机器人和看板打底。

一期先做群聊清洗与事件产出；二期再接入产品线监控（如 CDN / 存储）和用量计费等。后端统一用 Python，框架不限。一期不要求做看板或完整产品。

本仓库同时服务一次内部遴选：约 6 人各自实现，周一对比，预计选出 2–3 人继续做。对外说法常被缩成「写一个提示词」，实际要交的是能把聊天洗成事件的方案和可运行能力；提示词只是抽取层的一部分。要比的核心，是同一批聊天上的清洗质量，以及是否按后期执行方式来洗（增量产生并更新事件）。

## 2. 领导与官方要求

下面这些是已经对上口径、开发时必须对齐的要求，不是建议。

### 2.1 数据与范围

- 现在处理的是企业微信群聊（接口返回里群号带 `R:` 前缀）。以后还可能覆盖钉钉、飞书、网易泡泡等不同客户使用的 IM，所以取数要做成适配器，不要把企业微信字段写死到事件合约里。
- 已有企业微信机器人，能读群、改名、拉人、建群、发消息（当前偏 OCR / RPA，不一定是官方企微 API）。一期不要实现这些机器人动作。
- 完整系统是多源的：群聊、产品线监控、用量 / 计费。一期只洗群聊，但事件合约要能在二期被监控和用量复用，尤其是商机、流失、排障这三类。

### 2.2 事件与属性

官方六类事件是评分和交付的下限，不是上限。会议上明确说类型和属性「可能不止这几个」，并会看「谁做得好」：

1. 商机
2. 流失
3. 排障
4. 资源需求
5. 功能需求
6. 商务需求

公共属性至少包括：

- 类型
- 起止时间
- 状态
- 主要跟进人员
- 事件等级
- 内容概述

允许补类型专属属性，也允许在扩展字段里增加额外类型或信号。不要用自己的分类体系替换这六类。官方尚未公布状态、等级的枚举，以及扩展类型是否计入评分；实现时做成可配置，缺省值集中放置，并标明待确认。

输出分两层：先产出事件，再按角色分发、做日报周报、接机器人和看板。一期只把第一层做对、做能演示。

### 2.3 取数接口（2026-11-12 晚间正式说明）

葛波给出的接口：按 UID 和日期取聊天。

```bash
curl.exe -X POST "https://ts.qiniu.io/api/mars_alert/qq/chatRecords" \
  -H "Content-Type: application/json;charset=UTF-8" \
  -d "{\"uid\":\"1383603926\",\"start\":\"2026-11-11\",\"end\":\"2026-11-11\"}"
```

- 方法：`POST`
- 地址：`https://ts.qiniu.io/api/mars_alert/qq/chatRecords`
- 参数：`uid`、`start`、`end`；日期格式 `YYYY-MM-DD`，含首尾。
- 官方样例客户：`1383603926`。该客户从 2026-11-08 起有聊天记录，可以从 8 号开始洗。11-07 拉取为空。
- 已从当前 WSL / 公司内网验证可通（HTTP 200）。官方示例请求没有鉴权头。该接口在非内网环境可能返回 403，开发时默认在 WSL 内网跑。
- 这是周一演示和后续洗数的官方数据源。不要改用 mars 项目里的开发库或旧版 `GET /qq/messages`。

响应结构（已实际探过，字段名以接口返回为准）：

```text
{
  code, msg, uid, start, end, total,
  groups: [
    {
      group_number, group_name, total,
      records: [
        id, group_number, group_name,
        sender_number, display_name, nick_name,
        content, created_at, send_time, is_inner
      ]
    }
  ]
}
```

需要按实际行为处理的细节：

- `id` 是唯一数字字符串，用作消息幂等键。
- 记录在单个群内按 `send_time` 排序，但多群之间不是全局有序。处理某一天时，要把各群 `records` 合并后按 `send_time` 再排序。
- 事件时间用 `send_time`。`created_at` 是入库时间，通常比发送时间晚 1–3 分钟，不要当事件时间。
- `is_inner` 为 0 或 1，各群都有混合。官方含义尚未书面确认，可暂作「是否内部人员」的候选信号，用来辅助跟进人，但不要写成已定语义。
- 图片、文件在 `content` 里常表现为 `[图片]`、`[文件]`。当前没有单独的 `message_type` / 附件地址。
- 当前样例体量下，`total` 与实际返回条数一致，尚未观察到分页。分页、限流、离开内网后的鉴权都未正式说明，客户端要为以后补分页留出位置，但不要臆造协议。

### 2.4 洗数方式（必须按后期执行来做）

葛波明确要求：洗数方法要和以后真正执行的方式对齐，不能只图一次出结果。

- 按周期做增量洗，逐步产生事件，并更新已有事件。
- 必须处理跨天事件：隔几天之后还要能准确认回同一件事，不能重复创建，必须更新原事件。

处理周期可配置：默认 `PROCESS_INTERVAL=15m`；`1d` 用于五天逐日回放。周期、上下文回溯（默认 `3d`）、事件匹配窗口（默认 `7d`）、已关闭事件宽限期（默认 `7d`）和取数补漏回溯（默认 `2d`）是不同参数，缺省集中放在 `.env.example`，不视为官方规则。

业务时间统一为 `Asia/Shanghai`。程序内部采用左闭右开窗口 `[start, end)`，命令行仅填写日期时结束日期包含整天。在线来源现按分钟窗口及补漏范围请求；日期调用和旧离线日期缓存继续兼容。两种方式均需重叠补漏，并按来源及消息 ID 去重；交给当前周期的新增消息按 `send_time` 筛选，回溯上下文不得包含未来窗口消息。

推荐的执行循环（与技术方案一致）：

1. 用水位记录上次洗到的日期和最后一条消息的 `send_time` / `id`。
2. 只拉增量消息，按 `id` upsert。
3. 抽取时带上必要的回溯上下文（同一 UID 近期消息和未关闭事件），不要把历史全量反复塞进模型。
4. 先做批次内合并，再和该 UID 下未关闭事件、以及宽限期内刚关闭的事件匹配。
5. 命中则更新同一 `event_id`：延长结束时间、追加证据、刷新概述 / 状态 / 等级 / 跟进人；未命中才新建。
6. 记下事件在哪一天创建、后来被哪些消息更新，便于演示和核对。

跨天身份不要只看「类型相同」。同时满足更稳：同一客户 UID（可跨群，不要只按单个群）、同一主类型、同一主题对象（产品 / 故障 / 需求 / 商务等）、时间落在观察窗口内。窗口要能覆盖「隔几天」，不要因为静默两三天就关闭再开一条新的。若有明显的指代衔接（「刚才那个」「还是这个问题」）应一并考虑。吃不准时标为「待确认」，禁止悄悄拆开或合并。

## 4. 一期要做成什么样

官方一期验收重点仍是可运行的增量事件链路。用户另行批准加入本地网页，以便直接查看处理进度、事件证据和逐轮变化，不扩展角色分发、日报周报等业务。

现场应能看清三件事：

1. 输入是官方接口拉到的群聊（按 UID + 日期），不是手工粘贴的一篇静态文本就算完。
2. 输出是结构化事件列表，覆盖官方六类公共属性，带可核对证据，未知处不编造。
3. 将周期设为 `1d`，按 8–12 日逐日回放五轮，用的是和 `15m` 等周期相同的增量引擎：第一天创建的事件，后面几天若还是同一件事，应看到同一 `event_id` 被更新（结束时间延长、证据增加、概述刷新），而不是又多出一条重复事件。隔了几天的也要能认回。

每次回放结束在 `data/snapshots/` 留下事件快照和新建、更新记录。这样周一讲解时可以对着变化说，而不用翻原始聊天。快照可能含证据和概述，应与原始数据一样保留在已忽略的本地目录。

实现职责分层（按用户确认后的工程结构）：

```text
dake-aftersales/
  backend/              # Python 包、依赖、后端测试
    src/dake/
      api/              # FastAPI 请求与响应
      services/         # 取数、单周期处理、范围回放和查询
      ingestion/        # 官方客户端、统一消息适配器
      domain/           # 统一消息、候选、事件与窗口
      analysis/         # 抽取、校验、合并、跨周期匹配和更新
      repositories/     # MySQL、运行记录、本地水位与快照
      jobs/             # 后台处理执行器
  web/                  # Umi 管理端：事件、详情、处理记录
  docs/                 # 简报、方案、工程架构和接口定义
  compose.yaml          # 本地 MySQL
  .env.example          # 统一配置示例
  data/                 # 私有数据，已忽略
```

消息、事件保留原有表与数据；网页运行记录使用独立 `processing_runs` 表。运行状态属于程序执行状态，与官方尚待确认的事件状态枚举分开。

目录名可调整，但职责不要混在一个脚本里无法演示「更新而非新建」。取数客户端处理 HTTP；数据源适配器将原始记录翻译为统一消息；业务服务负责增量周期、抽取、匹配和更新；命令行负责输入参数和展示结果。

存储已确定使用本地 Docker MySQL 8.4，项目名 `dake-aftersales`，仅监听 `127.0.0.1:3307`，数据持久化到 `data/mysql/`。用户名与随机密码在本地 `.env` 配置，应用使用独立普通用户，不使用 root 账号。MySQL 初始化凭据只在空数据目录首次启动时生效，后续修改 `.env` 不会自动修改已有数据库密码。

业务数据保存在 `messages`、`events` 两张表。`messages.processed_by` 按 Provider / 运行流保存已处理消息的摘要，与事件更新在同一 MySQL 事务提交，作为权威处理状态。`data/state/` 下的本地水位用于选择下次运行窗口，不是唯一的去重依据；水位文件丢失后回放仍须避免创建重复事件。

目前命令行、FastAPI 与后台执行器共用业务服务；前端只经接口查询和提交处理。自动调度后续接入同一入口，不把业务规则写进命令行或 HTTP 层。

`fetch` 只取数、适配和存储，不分析事件；`replay` 在指定范围按周期连续执行；`process` 每次只执行一个周期，默认从本地水位继续，也可显式指定起点和截至时间。日期结束值包含整天，精确时间戳结束值不包含端点。自动调度尚未实现，命令不会常驻运行。

抽取层必须可替换：默认不得把未获授权的内部聊天发到外部 LLM。2026-11-13 用户已明确授权官方样例经其指定 XHub 清洗及本地展示；其他数据、截图或服务不自动获得同样授权。配置缺省仍为 stub，没有模型时，回放、存储、匹配也能跑通。不要把 API Key 写进代码或仓库。

竞争力不来自另起一套分类，而来自：官方六类做扎实、属性更完整、边界清楚、证据可核对、不幻觉，以及把增量身份和跨天更新做对。扩展信号单独放字段。

## 5. 事件合约（一期最小集）

每条事件至少包含：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 稳定 ID。跨天更新必须保持不变。 |
| `uid` | 客户 UID，不是群号。同一客户多群视为同一客户。 |
| `type` | 主类型，先用官方六类；扩展类型走扩展字段。 |
| `start_time` | 首次相关消息的 `send_time`，创建后一般不改。 |
| `end_time` | 随新的相关消息延长。 |
| `status` | 待官方枚举；缺省可配置，不要写死一套假装官方标准。 |
| `assignees` | 主要跟进人；可参考 `is_inner` 等信号，但语义待确认。 |
| `severity` | 事件等级，枚举待确认。 |
| `summary` | 内容概述，更新时应重写或修订，而不是只追加互矛盾的句子。 |
| `evidence` | 可核对证据：消息 `id`、`send_time`、必要的原文摘要。 |
| `attributes` | 类型专属属性。 |
| `extensions` | 额外类型或信号，不覆盖主类型。 |
| `created_on` | 哪一次洗数 / 哪一天创建。 |
| `updated_by` | 后来哪些消息、哪一天更新了它。 |
| `review_flag` | 吃不准时标「待确认」。 |

匹配与更新规则见 2.4。同一天、同一批次里抽到的重复候选，先合并再入库。
