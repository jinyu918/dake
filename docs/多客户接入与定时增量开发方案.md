# 多客户接入与定时增量开发方案

日期：2026-11-17。状态：四个接口已提供并完成小范围只读测试；分钟窗口及跨客户统一消息适配已实现；客户资料客户端、发现持久化及手动同步页面已实现；等级查询筛选已实现；群过滤、分析准入编排和自动运行仍待实现。

本方案整理已确认的线上接入流程：通过不传 UID 的分钟聊天接口发现窗口内活跃群及客户，逐步积累客户集合；群缺少客户 UID 时，通过关键词搜索相关群补查；确认 UID 后筛选大客户、获取主备负责人，再由定时器驱动现有增量服务持续处理。找不到 UID 或归属不明确的群暂不分析，保留待确认记录。

本轮目标为本周三（2026-11-18）的线上验收准备多客户运行能力。验收范围、部署环境、可接受延迟及接口完整性边界仍待对接；接口可调用不代表业务接入和持续运行已完成。

## 现有调试基础

2026-11-16 本地只读检查：官方样例客户已关联 3 个群，消息库有 632 条消息，发送时间覆盖 11 月 8–14 日；当前 XHub 分析版本有 29 条事件。运行记录共 6 条，其中最近一次完成 2304／2304 个窗口，另有 5 条历史失败记录。这些是本地检查时的运行计数，不是固定测试期望或清洗质量验收结果。

现有系统已经具备单客户多群取数、逐窗口分析、事件更新和网页展示，不重新搭建这条链路。客户发现已支持手动同步，后续补充客户筛选和持续调度，并验证多客户规模下的查询性能；现有样例继续用于联调，不代表多客户实时能力已验收。

## 沿用现有输出合约

“统一合约”是组员在现有结构上对齐修改，不是从零另做协议或重复开发。基础合约位于 `backend/src/dake/analysis/contract.py`，正式归属合约位于 `analysis/attribution.py`，现有正式模型输出版本为 `4.0`。

已有字段包括六类主类型、主题、概述、状态、事件等级、跟进人、类型专属属性、扩展属性及证据；归属部分包括决定、关联事件、可能关联事件、判断依据、具体变化和恢复／复发信息。分类标签与检索优化分别推进，新增字段或改变语义时共同对齐校验、持久化与页面，不另建一套独立写入流程。

| 决定 | 含义 | 当前正式流程的处理 |
| --- | --- | --- |
| `new` | 证据明确指向一个独立新事项 | 校验后创建事件 |
| `update` | 属于已有事项，并有新业务事实 | 校验后更新原事件 ID |
| `duplicate` | 属于已有事项，但没有新业务事实 | 保存归属记录，不新增业务修订 |
| `review` | 指代、归属或恢复边界依据不足 | 保存待确认原因、消息引用和可能事件，不依据该候选直接创建或更新事件 |

### review 的复核边界

`review` 表示“待确认、需要复核”，不是所有事件必须经过审批，也不是官方事件状态。它既可能由模型提出，也可能由程序因证据不足将原建议降为待确认。

当前已实现的是待确认结果及处理依据的记录与展示，没有完整的人工审核提交接口、审核队列或审核结论回写流程。不能把显示待确认当成人工审核闭环已完成。

成功提交的窗口仍会记录相应消息的已处理状态。待确认不等于等待下轮自动重试：同一分析版本普通重跑不会专门再次审理这些消息，当前也没有保证后续新消息会自动解决所有旧待确认项。

人工复核闭环作为待开发项单独评估：至少要定位原候选、展示消息和候选事件、记录复核人及理由，并在明确决定后通过同一业务服务校验与写入，保留原判断和新决定。具体操作、权限及交付时间尚未确定，本轮先记录这个缺口，不宣称已实现，也不让模型无限重试代替复核。

事件归属的 `review` 与群缺少 UID 的待确认是两个阶段：前者已有客户和消息，尚不能确定事项归属；后者客户归属尚未确认，根本不进入事件分析。两者不能共用一个含糊的“审核通过”动作。

## 当前已实现的客户交付

客户页面支持按时间范围手动同步、客户 UID 搜索、等级与负责人状态、关联群、待确认群及同步进度。同步复用现有持久任务执行器，按配置周期（默认 `15m`）分窗，单次最多一天、最多 500 个不同客户；原始聊天仅缓存于私有目录，客户同步不写分析事件。客户及映射与本轮任务进度同事务提交。

资料刷新失败保留成功旧值并标记过期；部分查询失败的任务保留已完成结果并明确失败。归属冲突保留历史及原 UID，待确认群不自动进入分析。当前没有人工复核提交、自动分析准入或定时启动，页面上的客户集合不等于已授权模型处理的集合。表结构及调用关系见 [工程架构](工程架构.md#客户资料与发现)，迁移及使用步骤见 README。

## 已确认的接入来源

四个官方接口已于 2026-11-16 提供并完成小范围只读测试，地址、字段、计数、分钟边界和完整等级表统一见 [项目简报 2.3.1](项目简报.md#231-新接口与客户等级2026-11-16-已正式说明)。不接入此前探查的 Mars 内部群列表接口或旧开发数据库。

| 接口能力 | 当前证据 | 开发用途及待核实边界 |
| --- | --- | --- |
| `POST chatRecords`，分钟参数、不传 UID | 返回跨客户群和消息，两层均有 UID | 发现窗口内活跃群并获取消息；不代表完整群清单，分页和截断规则未明确 |
| `POST searchGroups`，`keyword` | 返回群及 UID，同次搜索可有多个客户 | 缺 UID 时补查；需要关联依据，不能直接绑定首条结果 |
| `GET level?uid=...` | 返回 `data.uid/rank/level`，level 对应月销 | 保存等级与官方分层；已确认 L6～L10 算大客户，rank 含义仍待确认 |
| `GET tam?uid=...` | 返回 `data.uid/tam/tam_b` | 保存责任信息；核实主备语义、人员标识和缺失情况 |
| `POST chatRecords`，UID 加分钟参数 | 请求成功，本次样例窗口为空 | 补测非空 UID 筛选；保留原日期回放兼容 |

`ChatRecordsClient.fetch_window`、`ChatRecordsAdapter.normalize_window` 和 `OfficialChatSource.load_window` 已支持分钟窗口及可选 UID。共用摄入服务使用窗口来源协议，继续输出统一 `Message` 并复用既有增量和事件更新服务，兼容日期调用和旧离线日期缓存。窗口适配只负责统一消息；手动客户同步在独立业务服务中消费群身份字段，保存客户集合及资料，不触发批量分析。统一消息已含来源、消息 ID、会话和发送者字段，消息键为来源加 ID；后续平台各自增加适配器，跨平台客户身份映射另行实现，本轮不创建空壳平台。

完整群清单尚无已验证来源。第一版持续积累活跃群及客户，某窗口未出现的群不得据此删除、停用或判为不存在。以后若提供完整群清单，再补充发现来源；不能通过任意放大聊天窗口宣称已完成全量发现。

增量游标、消息变更类型、批量按消息 ID 查询、批量客户资料查询是建议支持的能力，目前未确认提供。消息游标若可用，应能覆盖服务端迟到入库和后续修订；事件业务时间仍使用 `send_time`。

## 客户发现和 UID 补查

正式运行不依赖人工预先提供完整 UID 清单。系统从分钟聊天返回的群数据中识别、补查、去重并筛选客户，持久化形成可处理客户集合；定时消息任务读取这个生成结果。人工维护只用于补充或纠正无法自动确认的映射。

保存客户集合是为了复用发现结果及资料，避免每个消息窗口重复查询所有客户资料。窗口取数提供发现线索，客户范围同步任务更新集合及资料，消息任务独立推进各客户的分析进度；发现与分析应复用已摄入消息，不重复拉取相同跨客户窗口。

处理顺序如下：

1. 按窗口获取跨客户聊天，检查响应条数及归属，保留接口来源、群 ID 和同步时间；完整群清单和分页协议未提供时不臆造。
2. 已明确命中供应商或内部产品群排除规则的群可提前跳过 UID 搜索。
3. 接口直接返回明确客户 UID 的，校验后保存映射。
4. 缺少 UID 的，从群名称等信息中提取有限关键词，通过官方相关群搜索接口补查。
5. 检查候选群与原群是否属于同一客户，形成确认映射或待确认结果。
6. 对已确认客户 UID 去重，查询客户等级，筛出允许处理的大客户。
7. 获取主备负责人并加入启用客户清单，供定时执行读取。

账号 UID、群 ID、客户 UID 必须分别识别。不得从群名数字直接生成客户 UID，也不得将关键词搜索的第一条结果直接绑定为客户。

即使搜索结果只有一个 UID，也要有足够关联依据。接口提供的正式群客户映射可以作为依据；仅名称相似时先保留候选，交由人工确认。多个候选 UID、无命中、分页不完整和接口失败要分别记录，不能全部当成“无客户”。一期不通过递归扩展搜索无限扩大范围。

未找到或无法确认 UID 的群不进入事件分析，不分配虚构 UID，不判为非大客户。保存群 ID、候选客户、查找依据、最后尝试时间和原因；支持有限重试及人工补充。查询失败不能覆盖已有已确认映射。

映射后续发生变化时保留历史，暂停冲突映射的自动使用，不将旧消息直接搬到另一客户。现有消息存储拒绝同一消息 ID 跨客户覆盖，该约束继续保留。

## 群过滤与客户筛选

群用途规则沿用 [群识别与消息过滤开发方案](群识别与消息过滤开发方案.md)：普通内部协作群与客户群保留，供应商名称规则和明确排除清单优先。当前样例三个群全部保留。2026-11-17 用户明确排除清单先预留、初始为空，不需要先收集实际排除群；名称规则不因空清单自动新增或启用。

2026-11-17 用户明确需要同客户跨群合并。现有流程已按 UID 汇集多群消息、检索历史事件并允许更新同一事件 ID，后续复用并验证这些能力；跨群不再是待确认限制，客户隔离和事项归属校验仍保留。

群过滤与客户准入是两道独立判断。未知群用途默认保留，仅表示不因群用途排除；如果客户 UID 尚未确认或大客户身份未知，仍不能进入自动事件处理。

UID 尚未确定时，只能使用明确适用于该来源的全局排除清单或已确认名称规则，不能套用另一个客户的规则。原群过滤方案的按 UID 配置继续用于已确认客户；若增加全局配置范围，需显式定义，不能通过缺省 UID 隐式扩大规则作用域。

2026-11-17 用户已正式确认大客户门槛为 `level >= L6`：L6～L10 属于大客户，L0～L5 不属于。筛选逻辑需集中实现并按等级数字或明确集合判断，禁止字符串字典序比较；未知或无效等级不能映射成 L0。门槛已接入客户查询及页面筛选，默认查看大客户，允许查看非大客户、等级待确认和全部客户；分析运行的自动准入编排仍待接入。刷新失败后保留的旧等级暂列等级待确认，不把资料失败当作非大客户。查询结果明确为非大客户时不纳入本期运行；首次等级查询失败或结果未知时待确认。已有客户的资料临时刷新失败时保留最后成功结果，标记过期并按明确的有效期策略使用，不能静默移除或无限期沿用。

主备负责人是客户责任信息，与事件实际跟进人分别保存。不能因为某人是客户主负责人，就断言其已经参与事件处理。负责人暂时缺失时标记未知，不编造，也不应单独阻断已确认客户的事件提取。

## 两类定时任务

采用外部定时器触发轻量执行入口，复用现有业务服务。第一阶段保持单实例和有限并发，不引入分布式任务平台，不在定时脚本中复制归属、分类或回放逻辑。

| 任务 | 工作内容 | 运行策略 |
| --- | --- | --- |
| 客户范围同步 | 消费窗口发现的群线索、补查 UID、更新等级和主备负责人 | 独立可配置频率，支持手动同步；不随每个消息窗口重复查询全部资料 |
| 消息增量处理 | 为启用客户补跑待完成窗口，生成或更新事件 | 处理周期缺省沿用 `15m`，定时触发频率与业务窗口大小分别配置 |

每次增量执行应做到：

- 读取启用 UID 清单，每个 UID 和分析版本分别维护进度。
- 使用 `Asia/Shanghai` 计算动态处理上界，优先处理完整窗口，可配置数据延迟缓冲；不继续使用演示的固定结束日期。
- 从已保存进度继续，按顺序补跑，限制单次最大窗口数和运行时间，避免某客户积压占满整轮执行。
- 一个客户失败不阻断其他客户；记录失败窗口，不跳过后续无法安全处理的业务顺序。
- 同客户不重叠执行，沿用客户锁及消息幂等；定时器重复触发时不重复领取相同任务。
- 重启后根据数据库处理状态与执行记录恢复。水位文件仅辅助选窗，丢失不能导致重复事件。
- 网络暂时失败可有界重试；事务提交结果不明必须先核实，不能盲目重跑。已提交但展示失败按原收据恢复。
- 定时任务接入 `processing_runs` 和既有执行记录，页面能看到处理范围、进度、失败与最近成功时间。

现有 `process` 每次仅执行一个窗口，`replay` 处理有限范围。新定时入口负责动态窗口和有界补跑，调用同一增量服务；首次运行起点按客户明确配置，不从最早历史自动全量分析。

## 取数和本地写入

分钟适配已实现，按当前窗口及补漏范围取数。接口实测包含结束分钟，内部仍按 `[start, end)` 过滤并去重；核对条数与归属，发现不完整时不推进进度。分页协议未明确，不臆造分页参数。只有发送时间过滤仍可能漏掉迟到消息，应保留重叠回溯；有正式变更游标时优先按其协议获取变化。未提供消息删除或修订能力时，明确记录边界，不假装已覆盖。

来源适配器统一消息后，继续按来源和消息 ID 幂等写入 MySQL：新消息新增、相同版本跳过、修订消息更新并进入相应待处理流程。补取历史不能把未来窗口消息提前交给抽取器。

原始响应、真实群映射及客户资料仅放本地私有存储，不写入文档、测试或普通日志。日期接口沿用现有按日缓存；分钟响应缓存已按来源、分钟查询范围及 UID 筛选条件隔离；以后接入分页时再加入分页身份，不能让不同请求相互覆盖。初期不删除既有消息或历史事件。

事件更新、证据关联及消息已处理标记保持原子提交。取数频率和业务分析频率可以分开，但不能形成两套重复的处理逻辑。

## 查询性能与存储职责

本地 MySQL 继续作为业务存储。先利用客户、时间、ID 的结构化字段和索引定位，再按需加载正文，避免把所有数据放进单块 JSON 后反复扫描。

- 群客户映射、客户等级和主备负责人需要可持久化、可查询的记录；按已实测字段设计迁移，保留字段语义未知和刷新失败状态。重复同步按稳定 ID 更新，不追加无界重复数据。
- 消息写入采用有界批量比对与写入，减少逐条查询往返。待处理消息的状态应可索引，避免每轮从项目起点扫描处理标记 JSON。
- 历史检索先读取少量事件标题、摘要、对象和时间，再读取候选关联聊天；会议提出的 30 天范围应作为可配置参数对接，不在此文改写当前运行配置。
- 变化面板已有明确事件关联、执行分页、轻量响应及按需详情加载；后续关系与索引设计以规模验证为依据，不重复列为从零开发。
- 完整模型输入输出保留为审计详情，展开时按需读取，不进入默认列表响应。

2026-11-16 已对照代码核实：`repositories/attempts.py` 支持 `002_event_link_hints.sql` 的生成列提示预筛选及精确关联校验，未迁移时回退原查询；旧任务通过 `JSON_TABLE` 提取关联，接口支持 `execution_offset` 和 `include_details`，前端首屏读取轻量结果、展开后读取详情。这部分已实现，从待开发项移出；本次仅核对代码，不宣称本地已应用 002 迁移或完成多客户规模性能验收。提示查询仍扫描客户分析范围内的轻量记录。

其余存储优化在实施时提供迁移和旧数据兼容方案，不能绕过提交收据或证据版本校验。是否增加语义检索由候选召回测试决定，不将向量数据库作为接入前置条件。

## 接口实测后的推进方式

四接口客户端、聊天窗口适配、客户发现持久化及手动同步页面已实现，接下来按“群过滤和客户筛选 → 多客户复用现有分析 → 持续运行 → 扩展页面及验收”推进。时间过滤依据、非空 UID 筛选和返回完整性继续补测，不把尚未明确的分页规则写死。归属更新、分类标签按已有分工对齐合约，不重复开发。

“用新接口跑通”指新接口输出统一消息后，实际经过原有增量分析、事件更新、执行记录和网页查询；单客户验证只是集成检查，不替代多客户持续处理验收。新增客户的线上模型处理范围仍须明确，原样例客户的 XHub 授权不自动扩展到所有发现的 UID。

大客户等级门槛已确认，不再列为待确认项。上线前还需落实部署机器、网络与鉴权配置、筛选逻辑及允许模型处理的客户范围、首次起点、运行周期、追赶上限及验收延迟；资料有效期、等级变化后的历史补跑和未结束事件处置仍待确定。允许处理范围是数据与模型使用边界，不要求用户预先手填完整 UID 清单；实际 UID 集合由发现流程产生。令牌和密钥通过本地私有配置提供，不放在命令行、文档或提交说明中。

## 验收场景

测试使用合成群、客户和消息；正式联调结果只记录计数、状态与耗时。

| 场景 | 预期结果 |
| --- | --- |
| 多群直接返回同一客户 UID | 维护多群映射，客户资料和增量任务按 UID 去重 |
| 原群无 UID，相关群有可靠客户关联 | 保存依据，确认后进入等级筛选 |
| 仅名称相似或存在多个候选 UID | 待确认，不自动绑定 |
| 无搜索结果或搜索接口失败 | 区分原因，暂不分析，支持重试 |
| 未知群用途且没有 UID | 不因默认保留而进入事件分析 |
| 命中明确排除规则 | 跳过分析，可提前省略 UID 搜索 |
| L5、L6、L9、L10 的准入边界 | L5 不纳入，L6、L9、L10 纳入；L10 不因字符串比较被误判 |
| 等级未知、首次查询失败或明确非大客户 | 分别记录，不能混为同一状态 |
| 响应条数不一致，或以后分页接入时只有部分页成功 | 标记不完整，不推进发现进度，不据此停用未返回的客户或群 |
| 当前窗口没有出现此前已发现的群 | 保留历史映射，不把静默当作删除或停用依据 |
| 多客户持续执行，其中一个失败 | 其他客户继续，失败窗口和进度可查询 |
| 定时器重复触发或停机后补跑 | 不重叠领取、不重复建事件，按窗口有界追赶 |
| 迟到、修订及时间边界消息 | 按接口能力补漏，幂等处理，不提前使用未来消息 |
| 负责人缺失或资料刷新失败 | 未知／过期明确，不编造、不覆盖有效资料 |
| 群 UID 映射冲突或变更 | 留痕并停止冲突绑定，不跨客户覆盖历史消息 |
| 从跨客户窗口消息启动，无人工 UID 清单 | 持续生成去重的客户集合并筛选，定时任务读取该集合；不宣称覆盖静默群 |
| 事件候选被判为 `review` | 留下原因和引用，不因该候选直接新建或更新事件；不宣称自动完成复核 |

交付为接口适配、群客户映射与待确认记录、客户筛选、定时执行入口、运行可观测性和回归验证。四接口已验证可调用；聊天窗口适配已接入共用业务入口，客户发现已支持手动同步和页面查询，等级查询筛选已接入页面，群过滤、分析准入编排及定时器尚未上线。
