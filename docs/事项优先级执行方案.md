# 事项优先级执行方案

2026-11-18 · 待实施

由一名开发者完成实现、联调和验收。首期由 AI 从当前事项的已授权消息判断跨客户影响。分别记录明确受影响和可能受影响的客户。后端核对客户标识与引文，按目录中的有效等级定档。告警接入一个能核对触发与恢复轮次的已配置告警来源。业务规则和示例以评审稿为准。 [事项优先级三维评审方案](事项优先级三维评审方案.md)

## 单人开发顺序

先固定合成输入、期望结果和读写契约，再按以下顺序逐项实现和验证。业务待确认项及其影响见第一节。

1. **事项定级与证据。** 在 `domain/priority_policy.py` 用 5×4 矩阵覆盖基础档，先修正 `high/immediate` 被判为 P0 的偏差。复用有效等级判定，分别保存基础档、客户调整和情绪调整后的计时前档。在抽取契约、校验和 `services/attribution.py` 中保留同窗不同候选的影响与情绪证据，核对发送人身份和报告 UID。
2. **事件写入与查询。** 接入明确归属和旧匹配两个入口。修正 `evaluate_priority_proposal(None, …)` 和 `queries.py` 按报告方档案重算现档的路径。确认 L9 受影响、档案变更、人工解锁时，用已保存事实重新评估。通过业务稿场景 1–6，再接入计时。
3. **计时与到期检查。** 用可控时钟逐格验证截止前、恰好到期和重复扫描。把阶段、原起点、计时前档、截止和超时结果与事件版本同事务提交。按索引分批扫描已到期事项，提交前复查版本。以场景 7–9 验收，并覆盖暂停、复查、终态、重开和并发更新。
4. **机器人告警。** 先验证轮次与去重，再在 `services/processing.py` 的客户事务中处理 `bot_pending`。场景 10 要覆盖同规则不同客户独立触发、同轮多客户、晚到恢复及复发。P1 提醒预览标明值班或 TAM，P2 标明客户负责人，P3 聚合，未知进内部兜底。实际来源待确认时可先完成合成用例，继续开发工作台。
5. **工作台与整体验收。** 接口确定后生成客户端，以同一事件 ID 核对列表、详情、筛选及人工裁定。最后在隔离库完成事务回归、固定窗口回放和本地试运行。

**契约冻结时需提交的三个合成样例**

| 样例 | 必须可区分的数据 | 防止的回归 |
| --- | --- | --- |
| L3 提报、中影响，事后证实 L9 受影响 | 原事件 ID、报告 UID、影响确认状态及依据、最高有效等级、基础 P2、生效 P1；取消待核实候选对生效档无影响 | 客户切换造成重复事项，或列表读取时按 L3 降回 P2 |
| 影响未知、明确情绪升级 | 基础待评估、计时前 P1、生效 P1、证据引用；风险复核与 P1 响应分别可见 | 错把未知影响当低影响，或把已有响应档的事项藏进未定档队列 |
| L8 局部降级、待接手恰满两个服务小时 | 计时前 P2、原起点、截止、本轮超时建议 P1、人工锁下的生效档；没有新消息仍可验证 | 每次扫描重算时限或重复升档，人工锁掩盖超时 |

工作台的“全部客户”在 `web/src/pages/events/index.tsx` 汇合各客户、各流的结果，`web/src/components/EventBadges.tsx` 会再次排序。让该比较器使用事件已保存的有效等级和截止时间，按时间戳比较带不同时区偏移的截止值。用同一组合成 ID 断言 API 与跨客户工作台顺序一致，同时保留客户切换器自己的排序。`RunRunner.notify()` 只唤醒本地调度线程，告警提醒预览随告警事务保存，未来接入实际投递时在提交后发送。

同档排序验收使用成对反例，依次固定前面的条件，只改变超时、有效等级、情绪或强催办、最早到期。其余键完全相同以事件 ID 稳定排列。尚无处理档的在途事项另按风险和复核截止排序；重大故障迹象优先人工复核，风险分组待业务确认，历史缺截止显示待核实。

## 一、业务确认与开发依赖

| 待确认事项 | 受影响的工作 | 确认前可完成的工作 |
| --- | --- | --- |
| P0 认定边界 | 事项定级正式试用 | 以业务稿为基线完成规则开发、样例回放和差异清单 |
| 处置时限及服务日历 | 超时自动写入 | 用测试日历检验到期、自然时间和服务时间，复核存量计时起点 |
| 首个告警来源、触发与恢复报文 | 实际告警来源接入 | 用合成报文验收告警分级、去重、复发和恢复，事项定级与计时可独立试用 |
| P1 告警接收人与提醒间隔 | 对接实际提醒分发 | 告警记录、待核实队列和提醒预览 |

## 二、阶段 0 · 统一输入与基线

| 工作项 | 交付及验收 |
| --- | --- |
| 旧版基线 | 固定授权范围内的回放窗口及合成样例。记录旧档、事件 ID、分析流标识和水位。选取能覆盖存量 `high × immediate`、客户等级失效和人工锁定的输入 |
| 共享字段 | 沿用 `base_priority`、`priority`、`priority_detail` 和 `version`，维持 `severity` 的兼容行为。约定明细里哪些字段承担事实、分步结果、计时与审计。约定旧事件缺字段时的读取行为，并以最小合成响应供前端开发 |
| 计时与告警样例 | 列出首条有效提报、接手、实质进展、重开和终态的证据用例。核对首个告警来源是否具备告警标识、轮次或等价可验证标识、触发与恢复事件时间、客户归属。输出缺项及对应待核实规则 |

合成用例按正常、边界和反例组织，至少包含未知影响但情绪升 P1、普通催办、确认跨客户影响、没有新消息时超时、历史恢复晚到。历史回放按当时已知消息和客户档案评估。无历史档案的客户等级标记待确认。

## 三、阶段 1 · 规则开发与定向验证

| 工作项 | 改动范围 | 前置 | 验收 |
| --- | --- | --- | --- |
| 三维定级 | `domain/priority_policy.py` | 共享字段、业务矩阵 | 先查影响面 × 客观时限，再应用客户等级、情绪或催办与超时规则。遍历矩阵及等级组合。P0 仅来自已证实的严重影响。影响未知且情绪明显升级时，基础档待评估，响应档 P1 |
| 证据抽取与合并 | `analysis/contract.py`、抽取提示词和 `services/attribution.py` | 共享字段，可用合成证据验证 | 独立保留客观影响、时限、情绪及催办依据。校验引文、发送人及事项关联。两个候选合并时验证客观档保留、情绪信号也保留。单句「尽快」、表情、机器人、转述和无关消息均有反例 |
| 计时纯规则 | 截止时间、状态和超时计算 | 共享字段及计时测试样例，可用固定计时前档位 | 用可控时钟验证恰好到期、跨休息日、内部等待、允许暂停后的复查、终态与重开。后续提档以原阶段起点计算。超时仅附加一次处理结果，连续重复检查保持同档 |
| 告警解析与分级 | 首个来源的规范化、轮次匹配和客户等级规则 | 合成报文先行，实际适配依赖该来源样例 | L9–L10 为 P1，L6–L8 为 P2，L0–L5 为 P3。多客户取已确认最高有效等级。缺归属或等级时进待核实。匹配触发与恢复使用稳定轮次 |
| 工作台界面与测试 | `EventBadges.tsx`、`ClassificationDetails.tsx`、`ManualDecisionDialog.tsx` 和告警列表界面 | 共享字段与合成响应 | 显示生效档、影响待评估、提档原因和超时标记。事项详情显示 AI 判定的受影响客户及其证据。告警用 P1–P3，待核实告警可见 |

计时和告警先以独立测试验证，接入事件版本和数据库的工作在下一阶段汇合。前端先用合成响应验证展示，接口确定后生成客户端。

## 四、阶段 2 · 事件写入、计时与告警接入

| 工作项 | 前置 | 交付及验收 |
| --- | --- | --- |
| 定级写入与影响客户认定 | 定级规则、证据抽取 | 在事件更新时保存 AI 提取的受影响客户及对应引文，身份或影响证据不足时标记待核实。保存确认依据、时间、采用的最高有效等级、规则版本和分步原因。事件归属及 ID 沿用原值。档案变更重评相关在途事项并留痕。人工锁作用于生效档，自动建议另记 |
| 截止时间查询与超时写入 | 计时纯规则、冻结事件写入字段 | 按阶段保存计时起点、截止时间和超时状态。采用可空、可索引的到期时间，按批查询。客户事务内重新核对事件版本、计时阶段、终态和人工锁。按事件和阶段实例识别重复检查。P2 到期升 P1，P3 到期升 P2，其他档按业务稿标记超时。存量缺可靠起点列入核对 |
| 告警存储与提醒预览 | 告警纯规则、触发和恢复字段 | 保存来源、告警标识、轮次、客户归属、原严重度及 P 档。轮次唯一键用来源、告警标识与轮次，投递去重用来源和消息标识。首次触发、确认更高等级客户和达到间隔的重复提醒按规则生成可去重预览。无法匹配轮次的恢复进入待核实 |
| 查询与前端联调 | 冻结字段可先接查询。完整用例依赖事件和告警写入 | 在 `services/queries.py` 读取新版记录已提交的档位及原因。列表、筛选、详情使用同一结果。排序依次使用业务稿约定的档位、超时、有效等级、情绪或催办、截止时间。导出 OpenAPI 后生成前端客户端 |

### 共享文件的接入与验证

| 范围 | 接入与验证 |
| --- | --- |
| `domain/models.py`、`repositories/mysql.py`、`backend/migrations/` | 添加计时投影、索引、事务读取字段及告警存储，检查新库和旧结构升级 |
| `services/processing.py` | 在原客户事务内接入告警处理，赶在相应消息标记完成前提交。同一窗口只有机器人告警时也执行该入口 |
| `jobs/runner.py`、`services/tasks.py` | 复用现有执行器安排独立到期检查。编排锁负责调度，处理批次使用客户事务。计时检查由可注入时钟驱动，空窗、无消息和重启均可启动检查 |
| 事件及告警 API、`docs/api/openapi.json`、`web/src/services/generated/` | 先核对字段语义和兼容样例，再导出 OpenAPI 并生成客户端，前端基于生成契约做联调 |

分析窗口开始时读取的事件，在提交前会核对修订基线。超时检查和人工裁定提交新修订后，窗口可能需要重新核对。并发用例须验证旧分析结果无法覆盖新修订、同一事件超时不会重复升档。提交结果不明时，先按事件版本、阶段标识或告警唯一键核实数据库中已提交的结果，再决定是否重试。 [窗口提交校验](../backend/src/dake/services/processing.py) · [客户事务](../backend/src/dake/repositories/mysql.py)

## 五、阶段 3 · 可重复验收与回放

| 验收线 | 执行方式 | 必须核对的结果 |
| --- | --- | --- |
| 后端规则与合约 | 先跑相关 pytest，用现有 `test_extraction_contract.py`、`test_attribution.py`、`test_classification_status_priority_domain.py`、`test_manual_decisions_and_queries.py`、`test_tasks.py` 和增量回放测试承接回归 | 正常组合、未知与过期、跨客户隔离、人工锁、同窗信号保留、事件详情与筛选一致 |
| 隔离 MySQL | 用 `scripts/verify_execution_mysql.py` 显式指定全新隔离库。事务竞态用例放进该入口会收集的 `test_execution_mysql.py` 或 `test_pipeline_mysql.py` | 扫描与人工裁定竞争、扫描与窗口提交竞争、两个扫描同时命中、服务重启后重跑、告警记录与消息处理标记的原子提交。同一阶段超时只生效一次，同一轮告警只建一条记录，同一投递只处理一次 |
| 工作台 | API 变更后生成客户端，从项目目录执行前端 lint、构建和定向 Playwright 用例 | 展示的生效档、筛选和排序与后端一致。影响待评估的情绪 P1 能找到。告警恢复只结束机器人告警，人工事项状态保持原值 |
| 同窗口回放 | 用固定 `[start, end)` 窗口、当时可用的客户档案和可控时钟运行新旧规则。回放文件保留在已忽略的本地数据目录 | 逐条核对新进或退出 P0/P1 的事项、档位依据、事件合并与归属、每种超时和告警的通知预览次数。记录总量和仍待确认的事项 |
| 分析流兼容 | 比较修改提示词或抽取合约前后的 XHub 流标识，检查该流对应的事件版本、客户水位、消息处理标记和收据 | 流标识不变时验证原事件可接续。流标识变化时，先在独立库证明承接路径可保留既有事项和窗口进度，再接入小范围试运行 |

在仓库根目录的验证命令如下。隔离 MySQL 入口所需的主机、端口、库名、账号和密码文件使用独立测试环境的实际参数。 [隔离验收入口](../scripts/verify_execution_mysql.py)

```powershell
.\.venv\Scripts\python.exe -m pytest -q backend/tests -m "not mysql and not isolated_mysql"
.\.venv\Scripts\python.exe scripts/export_openapi.py
npm --prefix web run openapi
npm --prefix web run lint
npm --prefix web run build
npm --prefix web test -- classificationStatusPriority.spec.ts
```

每项功能完成对应回归及业务确认后可单独进入试运行。三项功能都接入后，再跑一遍完整回放和工作台联动用例。

## 六、阶段 4 · 小范围启用与回退

1. **预览。** 在本地选择已授权的客户范围，以只记录对照结果的方式预览新档、超时及告警。核对 P0/P1 的变化、缺可靠起点的历史事项和待核实告警。记录当前分析流、规则版本及最后一个已完成窗口。
2. **启用。** 在完整窗口边界切换事项定级。抽查既有事件 ID、水位、消息处理标记和收据。定级稳定后开启到期写入。告警来源通过验收即可独立开启告警记录及提醒预览。分别核对一轮重复扫描、告警重复输入及服务重启后的记录数。
3. **观察。** 记录等级变动数、误提档、漏升档、重复告警、待核实积压和异常窗口。每条显著差异保留规则依据和业务复核结论。按业务确认的样本和实际运行结果确定试运行结束时间。
4. **回退。** 定级异常时停用新规则并恢复已验证版本。计时异常时暂停到期写入。告警异常时暂停告警接入或提醒。切换后分别核对最后已提交窗口与事件版本。已提交的异常结果按人工裁定修正，保留审计记录和处理收据。
